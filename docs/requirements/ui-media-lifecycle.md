# UI, media and lifecycle — functional requirements

**Current status:** the status of each requirement in this document, the implemented scope, the remainder and the documentation are in the [coverage matrix](coverage/ui-media-lifecycle.md) (rechecked 2026-10-20, ARC-DEV-027). The "Steamwoven" fields below and the summary coverage section give details as of their last edit (initial audit 2026-10-09, merged main [`a8a553b7`](https://github.com/Simarglok/arcanum-steamwoven/tree/a8a553b7c406ace77ea019bf2b13251f00ecddb6), PR #54); where they differ, the matrix is right.

**Research cutoff:** 2026-10-02. **Scope:** main and gameplay screens, the player's access to systems through the UI, movies/slides/sound, game session start, settings and save/load. This is a domain section of the shared catalog, not an audit of every game function, resource or every branch of each function group.

**Basis.** The functions of the original executable 1.0.7.4 at the listed addresses and the current Steamwoven `main` at [`b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae`](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae), PR #36 cutoff, were researched. The Steamwoven status catalog lags up to PR #30; here the state was checked against the code of the pinned HEAD. "Original observation" is a reading of original functions at the listed addresses, level F0 (not checked in the exe), unless the row is in the [verification ledger](../research/original-verification-ledger.md); it describes only the functions read and the caller chain. "Project proposal" and the Pre-alpha/Later phases are proposed for review by an experienced player and are not an already accepted contract. "Unknown" marks open function branches, data, platform limits and original runtime behavior.

Rules for selecting and loading modules and resources belong to [data, compatibility and modern targets](content-product.md). Clock/pause belong to [time and lighting](lighting-time.md); character formulas to [characters and skills](characters-skills.md); item and trade effects to [items and economy](items-economy.md); combat transitions to [combat, magic and technology](combat-magic-tech.md); dialogue history and script to the relevant story/social/AI documents. This section requires a surface accessible to the player and a correct transition between modes, without duplicating domain rules.

### FR-UI-001 — Main menus and start of a single-player session

**Proposed phase: Pre-alpha.** The player can reach a start screen, single player, new game, creation or choice of a prepared character, loading a continuation, settings, credits and exit. The main menu shows only the functions supported by the current game profile. The choice of campaign/module at the UI level is passed to the content-loading boundary; the rules for module search, priority and admission are not set here.

**Original observation:** the main menu has Single Player, MultiPlayer, Options, Credits and Exit Game; the Single Player window has New Game, Load Game, Last Save, View Intro and Cancel; the New Game window has Pick Character, New Character and Cancel (checked in the exe by two readings, [MM1–MM7](../research/ledger/ui-audio.md#main-menu-arc-ui-011)); the menu then leads to a new game or a preset character. In the menu launch (0x541180), different window types set in-play/locked/options states, and opening the settings (0x589280) in the menu builds a module list and disables that control in the game. The buttons and the transition into single player, creation of the character menu (0x5446A0, 0x5446D0, 0x5446F0), the character creation branch (0x545780, 0x545870, 0x5458D0, 0x5459F0, 0x545B60), the module control and the ban on changing it in the game (0x589280). Steamwoven: the main menu in the AREA viewer with `--main-menu` ([ARC-UI-011](../rendering/terrain-viewer.md#main-menu-arc-ui-011)); the settings window is [ARC-UI-013](../rendering/terrain-viewer.md#options-window-arc-ui-013); menu ↔ game transitions are [ARC-UI-012](../rendering/terrain-viewer.md#scene-flow-arc-ui-012): the in-game menu (window 3, and window 4 on another's turn in a turn-based round) and Quit, which resets the game, reloads the module and opens the main menu again (0x541180, 0x541B50, 0x549310, [SF1–SF5](../research/ledger/ui-audio.md#scene-flow-arc-ui-012)); the Godot entry page of the ART viewer remains a diagnostic inspector. [Viewer app surface](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L82-L103).

**Dependencies and scenarios:** character, start map, settings and content-product module admission. Check a new/preset character, cancelling before the start, choosing another module before entering the game, and resuming an available save. Character import/export is not assumed separately. **Steamwoven:** only DAT/ART/terrain tools; there is no menu data or production UI. **Unknown:** the full launch lifecycle of the original and module-choice errors were not run here.

### FR-UI-002 — In-game HUD, hotkeys and contextual control

**Owner clarification 2026-10-04:** keyboard/mouse keep the original actions, layout and UI semantics; custom controls and interface belong to the gamepad. Detailed bindings, contexts and confirmation boundaries are collected in the [single document of original input requirements](original-keyboard-mouse.md). WASD do not control the character. Diagnostic commands need a separate layer and do not take ordinary game keys.

**Proposed phase: Pre-alpha.** While exploring the world, the player sees the character's state and the available action panels, controls the combat/skills/spells modes, assigns and runs actions from ten quick slots and two recent actions, chooses a target and gets feedback on hover/contextual action. A click, an item drag, targeting and a UI hotkey must have a defined input owner while modal screens are open.

**Original observation:** the game interface functions (0x549B70–0x557CF0, 160 functions) route messages between the scrollbar, hover handlers, hotkeys, the active dialog filter, the combat turn and the bottom buttons, including opening the menu through the clock button and calling the spell/skill/combat panels. The quick slot launch (0x57D840) creates ten slots and two recent-action buttons, and its event handler (0x57DC60) handles events/drag. The compact panel (0x5689D0–0x5695A0) draws the health/fatigue bar, but the hotkey component declared in it has empty init/message/draw bodies (F0) and does not confirm a working compact quick-action panel. Main game input handling and the clock/menu branch (0x54B5D0), quick slots and recent actions (0x57D840), UI hotkey events (0x57DC60), the implemented compact health/fatigue draw (0x569070), the declared hotkey component and empty hooks, stub implementations of the hotkey hooks (0x569570, 0x569580, 0x569590, 0x5695A0). The health and fatigue bars of the PC, the hovered creature and followers were checked in the exe (ARC-UI-017, [CH7–CH9](../research/ledger/ui-audio.md#combat-hud-arc-ui-017)). Steamwoven has no production actor/HUD, only a diagnostic world viewer and a separate input experiment. [Limited viewer surface](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L82-L165), [boundary of the synthetic input settings model](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Input/InputSettings.cs#L5-L47).

**Dependencies and scenarios:** UI mode stack, input mapping, combat/skill/spell targeting, item actions and the shared message queue. Check synthetically hotkey assignment/replacement, the two recent actions, the priority of the modal/dialog filter and pointer/keyboard transitions without double activation. **Unknown:** the bindings and verification limits by original function are refined in the [original input specification](original-keyboard-mouse.md); the original runtime, localized resources and physical comfort need a separate check. Code UI ids alone do not establish a product layout.

### FR-UI-003 — Window modes, dialogue and transition between actions

**Proposed phase: Pre-alpha.** The dialogue shows the permitted lines and accepts the chosen reply. A transition dialog → trade, character/follower sheet, world map, schematics, identify/repair or back to the game world opens exactly the needed surface and closes the previous one in the right order. Open windows block only the actions that the domain rules forbid; an error/cancel returns the player to an understandable previous state.

**Original observation:** dialog entry (0x567460) checks the state of the participants, allows the dialog to open, gets the DLG and starts the text-conversation UI. When a reply is chosen, line handling (0x567E30) routes the result into a further line, the end, barter, character sheet, world map, schematic, identify or repair. The interface mode change (0x551A80) maintains the mode stack and calls close/open handlers. Dialog entry and mode start (0x567460), transitions by the chosen line (0x567E30), stack and window mode handling (0x551A80), dialog text options bridge (0x553320, 0x553350, 0x553370, 0x553380, 0x5533A0). Steamwoven has a DLG reader and a limited headless Direct-transition runtime; this is not a dialog screen, NPC invocation or game UI integration. ARC-SCRIPT-005 added a [multi-step conversation runtime](../scripting/dialog-conversation-runtime.md) and a diagnostic modal conversation panel in the AREA viewer (a click on the NPC and on a line, as in the original; keys are not redirected); transitions to trade/sheets/world map and others are shown as blocked, with no effects. [Current viewer screen](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L82-L103), [isolated diagnostic display lab](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L3-L16).

**Dependencies and scenarios:** [story/dialogue runtime](../requirements/README.md), DLG data, barter/items, character/social state, target identity and modal focus. Check a reply action → each screen, and closing/cancelling with the active mode restored. The UI does not repeat line validity, quest consequences or economic formulas. **Unknown:** the transition codes on incomplete/erroneous branches and the full DLG/SCR semantics need a separate check.

### FR-UI-004 — Inventory, Character screen, Logbook, map, records and companions

**Proposed phase: Pre-alpha for access to the key screens; full content/all submodes Later.** The player needs game panels for their own and an accessible other inventory, equipment/character, trade and loot/steal/repair; separate actions open the logbook, world map/travel, a book/note, a found technology schematic and the companion list with commands. Each panel passes item, character, world and story changes to the matching rule owner.

**Original observation:** opening the inventory (0x572240) serves several different inventory modes; opening the character sheet (0x5597C0), the logbook (0x53F020), the world map (0x560760), a written object (0x56BB60) and switching a schematic (0x56D130) create the dedicated screens; a schematic, a written object or a dialog reply have separate callers. The companion window message filter (0x56A9D0) passes companion commands to the order/target, inventory/barter and character views. Inventory and modes (0x572240, 0x572340, 0x572370), character sheet open (0x5597C0), logbook and world map (0x53F020, 0x53F090, 0x53F0D0, 0x53F0E0), world map open (0x560760, 0x560790, 0x5607E0), written objects (0x56BB60, 0x56BC00), schematics (0x56D130), follower actions/callers (0x56A9D0). Steamwoven has only diagnostic scenes/labs; the main HUD and the character/inventory/trade/journal/map/dialog panels are not implemented. With ARC-UI-007 the AREA viewer opens, on `C`, a diagnostic character sheet of the session hero, view-only; opening/closing, the refusal for a dead PC and the display of values were checked against the original exe ([viewer](../rendering/terrain-viewer.md#character-sheet-arc-ui-007)); with ARC-MAGIC-008 the sheet has the original's spells page (16 colleges, ranks, tooltips, `+`/`−` through the points path, [viewer](../rendering/terrain-viewer.md#spells-page-arc-magic-008)). With ARC-UI-008 the `L` key (the original's key, row [LB1](../research/ledger/ui-audio.md#logbook-arc-ui-008)) opens a diagnostic logbook with rumors and quests tabs ([viewer](../rendering/terrain-viewer.md#logbook-arc-ui-008)). [Viewer class surface](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L7-L17), [synthetic UI lab boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L63-L65).

**Dependencies and scenarios:** [items and economy](items-economy.md), [character and skills](characters-skills.md), world map, dialog/story and companion domains. For each screen check open/refresh/close, keeping a valid selection state, the transition into a dependent mode and no repeated call of a gameplay mutation. **Unknown:** the full content of records and the original UI labels were not studied here.

### FR-UI-005 — Dialogue line choice, messages, tooltips and floating text

**Proposed phase: Pre-alpha.** The player understands the hovered object/action, sees the chosen dialog options, result messages, status text bubbles and floating notices tied to an object. Hints do not cover the available options without cause, text does not stay tied to the object's old position, and the duration/visibility settings apply consistently. Long lines and the dialog window must have predictable wrapping or scrolling.

**Original observation:** the dialog option functions (0x4C9280–0x4C9BE0) draw up to five dialog options, highlight them with the mouse and select on press; by reading (F0) the red text color branch is not used, and the horizontal bounds of the options are not limited. The text bubble functions (0x4D5B80–0x4D67F0) draw bubbles above objects and remove them on a timer; the floating text functions (0x4D4E20–0x4D5DC0) keep per-object text lists and smoothly change position/opacity, with level and speed taken from the settings. Dialog option rendering and mouse selection (0x4C9720, 0x4C9810, 0x4C9A10), object bubbles and expiry (0x4D5EB0, 0x4D5F10, 0x4D5FE0), floater tick (0x4D5190), draw (0x4D5310) and creation (0x4D5450), level and speed settings (0x4D5B10, 0x4D5B40, 0x4D5B60). Steamwoven has no production game text/floater layer; the synthetic display lab checks independently authored layout geometry only. The ARC-SCRIPT-005 diagnostic panel shows the decoded NPC line and up to five numbered options with line wrapping. ARC-UI-005 added to the AREA viewer a hover tooltip (the object name as given by the original's object inspection (0x441B60), selection as in the original skipping `OF_CLICK_THROUGH`) and a left-click action cursor (project policy: the original cursor does not change with the target), see [viewer](../rendering/terrain-viewer.md#hover-tooltip-and-action-cursor-arc-ui-005); ARC-UI-057 checked against the exe the highlight of the hovered object (a repeated additive draw with color (200, 200, 200), 0x43C690) and its description in the message window (0x553BE0), see [viewer](../rendering/terrain-viewer.md#hovered-object-window-and-highlight-arc-ui-057) and [OH1–OH9](../research/ledger/ui-audio.md#hovered-object-arc-ui-057); bubbles and floaters are not implemented. The floating combat text was checked in the exe (ARC-UI-017): colors, rise, line overlap, fade, setting levels and the damage and message texts ([CH10–CH12](../research/ledger/ui-audio.md#combat-hud-arc-ui-017), [plan](../research/combat-hud.md)). [Exactly the synthetic UI scope](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L5-L16), [not a production UI decision](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L63-L65).

**Dependencies and scenarios:** the shared UI text layer, localization, font metrics, viewport anchors, dialogue log, text-speed/float settings. Check long multi-line replies, a narrow window, a scale change, closing a line, moving/removing the source object and turning off floating notices. **Unknown:** the actual original fonts, all clipping and the completeness of keyboard/gamepad accessibility were not assessed.

### FR-UI-006 — Available gameplay, video, text and audio settings

**Proposed phase: Pre-alpha for gameplay and volume; Later for additional display/input controls.** Settings must separate persistent user preferences from the state of the current save. The original's settings profile (F0) includes difficulty, violence filter, combat mode, auto-attack/weapon-switch, run and follower skill options; brightness, text duration, floating text/speed and combat taunts; separate effects, voice and music sliders. A modern project also needs a consistent screen for choosing display mode, scale, controls and key rebinding, if these functions are part of the accepted product contract.

**Original observation:** the settings control table contains three sets of game/video/audio controls; the module selector is disabled in the game. Brightness passes from the setting to the gamma API. Three volume sliders keep their values in the settings; the sound initialization (0x41AA30) registers their callbacks, which update effects, voice and music. The three tables and the specific controls, initialization of the selected tab and the module guard (0x589280), brightness binding (0x4BE0B0, 0x4BE0E0, 0x4BE0F0), the real volume-slider get/set callbacks (0x589960, 0x589980, 0x5899A0, 0x5899C0, 0x5899E0, 0x589A00), registration and application of the volume callbacks (0x41AA30), channel level updates (0x41C8A0, 0x41C8B0, 0x41C920, 0x41C930, 0x41C970, 0x41C980), settings file read/write (0x438B50, 0x438C20). The checked options table has no resolution/window mode or keybinding editor; this is not an exhaustive search of every input path. Steamwoven: the original's options window in the AREA viewer ([ARC-UI-013](../rendering/terrain-viewer.md#options-window-arc-ui-013), checked in the exe by two readings, [OP1–OP8](../research/ledger/ui-audio.md#options-window-arc-ui-013)): a table of 16 controls on three pages, their `arcanum.cfg` settings and defaults; the controls that have an action are shown (difficulty, combat mode without quick turn-based, auto-attack, Always Run, three volumes), the rest are hidden with a reason; the separate `InputSettings` model of joystick deadzone/sensitivity/camera inversion is neither game options nor remappable keyboard bindings. [Input settings codec](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Input/InputSettings.cs#L5-L47), [the UI lab explicitly leaves game settings/UI outside its boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L63-L65).

**Dependencies and scenarios:** settings persistence, platform display/input services, audio mixers, character auto-level policy ([character domain](characters-skills.md)). Check each tab, recovery after reopen/restart, independent volume channels, an unsupported display mode, key conflict/reset, and make sure a save slot does not change when a user preference is edited. **Unknown:** user-facing control for brightness/text-speed beyond the original's option fields and all original keybinding choices need data/runtime checks.

### FR-UI-007 — Adaptive composition and window accessibility

**Proposed phase: Pre-alpha for the modern target platform.** Game screens must keep access to important buttons, lists and text at different window sizes, high-DPI and the chosen scale. Windows must not cover important game data; scrolling, keyboard focus, cursor position and gamepad focus must have explicit rules. This is a project UI policy and not a claim that the original screens were responsive.

**Original observation:** the screens are laid out for an 800×600 base (F0); the matched functions in the original exe have no offsetting of elements relative to window geometry and no reading of the HighRes configuration (Width/Height, Windowed, scroll settings, intro/logos). The game library's resize (0x4025C0) passes resize callbacks to the modules. This is legacy positioning infrastructure, not a check of all screens at modern sizes. In Steamwoven the display lab checks synthetic logical layouts, not production menu/game surfaces and not physical readability. [Stated synthetic boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L28-L30), [not production UI or physical certification](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L49-L65). The accepted project direction requires modern resolution/high-DPI/scalable UI and first-class gamepad; this is product policy, not a conclusion from the original. [Architecture direction](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/architecture/decisions.md#L10-L15).

**Dependencies and scenarios:** viewport-independent simulation, text and input focus contracts, display settings. Check the production menu, dialog, inventory and save list at the target extreme aspect ratios, scales and keyboard/gamepad focus, and collect human visual/physical-device evidence separately. **Steamwoven:** the synthetic lab has limited layout verification; production UI integration and physical readability are not covered.

**Separate camera pan.** Scrolling menu content and moving the world viewport are different intents. The original has keyboard-arrow and mouse-edge callers; the scroll start (0x40E0A0) takes the speed/distance settings into account and, in the selected limiter branch, Perception; player load/move updates the center (keyboard caller (0x401560), mouse-edge/keyboard handler (0x401560, 0x401F50, 0x402010), camera/limit policy (0x40E0A0), viewport/listener update (0x40E630, 0x40E890, 0x40E8A0, 0x40E8B0), PC load (0x40D7C0), PC move (0x444270)). The accepted modern gamepad/follow/zoom contract is described separately in FR-PRODUCT-003; these legacy handlers do not prove its implementation. Proposed scenarios: pan/stop, the declared distance limit and centering without changing actor state; the mouse-edge mode and the exact original limit need their own decision/check. The current diagnostic pan is not a production original-limit policy.

### FR-UI-008 — In-play menu, modal guard and consistent pause

**Proposed phase: Pre-alpha.** The player can call the menu from the game interface. The menu hides the game frame when needed; in forbidden actions it stays in a safe locked state. The pause blocks exactly the world simulation according to the time policy, but the menu, input, fade and the needed interface/real-time events stay responsive. Closing restores the previous screen/mode with no missed input.

**Original observation:** on launching a non-options menu, the menu launch (0x541180) calls an internal pause-count helper and hides the main interface; the clock button chooses the ordinary or locked in-play menu depending on the dialog/world-map/combat-turn guard. The clock update (0x45B370) updates the real clock separately and skips the ordinary game time advance during pause, and the main menu has its own event loop. Menu open/pause-count branch (0x541180), clock button locked/open decision (0x54B5D0), pause count helpers (0x45B320, 0x45B340, 0x45B360), time domains during pause (0x45B370). See the [global clock/pause rules](lighting-time.md), without repeating their numeric profile here. Steamwoven has no game screen/mode stack or pause state; the viewer playback pause concerns only the inspector timeline. [Separate diagnostic timeline](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L104-L158).

**Dependencies and scenarios:** a single clock/pause owner, dialog/combat turn states, UI stack and real-time event policy. Check opening/closing of each permitted menu state, the ban on another's turn, that a UI redraw does not speed up the world, and menu/input responsiveness during pause. **Unknown:** the full set of causes of the internal pause gate and the original executable's response are not independently confirmed.

### FR-MEDIA-001 — Starting and playing movies

**Proposed phase: Pre-alpha for the unconditionally needed start scenes with a safe skip; full library/variants Later.** When a movie is requested, the player sees the video and the synchronized track, can skip it with permitted input, and a failed media open does not leave a black screen or a hung menu lifecycle. Intro/logo toggles, the order of display and fade-in/out belong to the active profile. Format support must be determined by the actual decoder of the target platform.

**Original observation:** the startup (0x401000), after loading the default module, requests movie id 8 (the show condition was not checked in the exe; the original has no intro toggle from the HighRes configuration in the matched functions); the main menu calls intro ids, playback by path (0x40DEE0) extracts the resource to a temporary path, blocks game sound and calls the TIG library's movie player. The movie open, the response to an open error and the key interrupt inside TIG were not read in the exe; the actual availability of codecs on the target platform is not established. Startup caller (0x401000), movie path extraction and TIG call (0x40DE70, 0x40DEE0). Steamwoven has no movie/game media playback surface; its video/image use is diagnostic ART inspection. [Viewer-only media scope](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L82-L140).

**Dependencies and scenarios:** content-product supplies movie asset/reference; platform media decoder, audio focus, input cancellation and fatal/nonfatal error contract. Test valid, missing/unsupported movie, keyboard skip, fullscreen state and return to menu; verify target OS separately. **Unknown:** no original playback symptom or actual retail movie has been checked in this research.

<a id="fr-media-002"></a>

### FR-MEDIA-002 — Scripted slides, death, endings and credits

**Proposed phase: Pre-alpha for a clear end of a failed playthrough; all ending/credits sequences Later.** Script-selected slides form an ordered presentation with fade and narration. Missing image or voice assets produce a deliberate fallback/error result. Skip input has explicit scope: skip current card or remaining queue. Ending selection must come from story/game state, not UI guesswork.

**Original observation:** slide start (0x569600) prepares a type-specific script queue; death uses a default entry only when the script enqueued none. Each queue item requires both a BMP and an MP3 voice path in the asset lookup (0x569930); the slide loop stops when the slide handler returns false after Escape. Credits fade in on return. Queue setup/fallback and presentation lifecycle (0x569600), script selects queued slide IDs (0x569720), slide display/input and queue stop (0x569770), paired media lookup and fade (0x569930, 0x5699F0, 0x569A60). Steamwoven shows the default death slide and resets to the main menu after the hero's death as the original does ([ARC-UI-026](../rendering/terrain-viewer.md#hero-death-arc-ui-026), ledger [PD1–PD9](../research/ledger/ui-audio.md#hero-death-arc-ui-026)); it runs no script-queued slides and has no story conclusion or credits UI. Its lab’s bilingual example text and images are synthetic and do not implement game narrative screens. [Display UI lab contents policy](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L3-L16).

**Dependencies and scenarios:** script/story state, narrative resource mapping, audio focus and menu lifecycle. ### FR-MEDIA-003 — Effects, voices and music with independent settings

**Proposed phase: Pre-alpha.** The game provides distinct effects, dialogue voice, ambient and music channels with independent user-facing volume controls. Voice can start/stop with the dialogue speaker; sound effects can be triggered by in-world actions; a failed audio backend must not invalidate unrelated world state. User volume preferences persist across saves/launches.

**Original observation:** sound initialization (0x41AA30) loads the sound effect index, music/ambient scheme indices and positional sound parameter data. Options exposes effects/voice/music controls. Dialogue speech start stops any prior voice handle before resolving a speech path and playing voice audio (voice gender is the PC's, ledger row [SN22](../research/ledger/ui-audio.md#audio-arc-res-052)); the stop routine destroys and clears the active handle. The TIG sound startup and its result on a failed audio device were not read in the executable; supported codecs and audible output are not established here. Sound tables and scheme initialization (0x41AA30), separate volume controls, speech start and stop bodies (0x5688D0, 0x5689B0), dialogue caller (0x568540). Steamwoven has no game sound, voice playback, or audio options runtime; the diagnostic ViewerApp controls only ART animation. [Viewer controls are for ART playback](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L104-L123).

**Original check and plan:** [ARC-RES-052](../research/audio-evidence.md) checked these mechanisms against `Arcanum.exe` 1.0.7.4 (three channels Effects/Voice/Music 0–10, voice by PC gender, footsteps, item and creature sounds), recounted all the module's sound data through the content stack and split full sound into tasks ARC-DATA-040 … ARC-UI-044.

**Dependencies and scenarios:** platform audio service, sound resource profile, options persistence, dialogue lifecycle, combat and item/world events. Check muted/independent channels, missing device/startup, voice cancellation on dialog close (in the original the voice keeps playing after closing, SN22 ARC-RES-052), and no simulation corruption when playback fails. **Unknown:** decoded file format set, actual device support, latency and cross-platform quality remain untested.

### FR-MEDIA-004 — Ambient/positional sound and sector scheme transition

**Proposed phase: Pre-alpha for the base map and voice/effect cues; full coverage of types Later.** Ambient/music scheme follows the active map/sector, transitions without stuck or duplicated tracks, and resolves combat music back to the active world scheme. Object-relative sounds attenuate and pan according to profile. Footstep cue selection may depend on surface and equipment but must not be guessed from renderer asset names.

**Original observation:** the sector object list (0x4F2330) applies a sector's music/ambient scheme on sector change. Scheme play (0x41BD50) supports two active schemes and fades replaced slots; combat switches to a stinger/loop pair and restores saved schemes when it ends (checked in the executable, ledger row [SN17](../research/ledger/ui-audio.md#audio-arc-res-052)). Positional parameters derive attenuation/pan from source/listener coordinates and data-controlled radii. Critter sound selection (0x4F0ED0) chooses footstep variation from material and armor (its off flag is tested on the local PC, ledger row [SN24](../research/ledger/ui-audio.md#audio-arc-res-052)); animation callers (0x421B00–0x437D00) trigger that choice during footsteps, while their full timing/action branch was not exhaustively inspected. Sector change caller (0x4F2330), scheme switch/fade (0x41BD50), spatial attenuation and panning (0x41B420), combat music and restore (0x41C4D0, 0x41C5A0), surface/equipment footstep selection (0x4F0ED0). Steamwoven has no sector audio schemes, actor events or production audio integration. [Diagnostic view entrypoint](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L82-L103).

**Original check and plan:** [ARC-RES-052](../research/audio-evidence.md#music-and-ambient-schemes-combat-music-save-and-map): the map scheme at each open, the sector pair when the local PC enters (0/0 is skipped), combat music from NPCs with a return to the last requested pair, positional attenuation with volume by size; the 20 night entries with a reversed clock-hour window do not play in the original.

**Dependencies and scenarios:** sector/map records and loaders ([content-product](content-product.md), [world](world.md)), time and ambient transition policy, combat owner, platform audio. Check crossing sectors with different schemes, repeated enter/exit, combat begin/end, source moving across listener, disabled sound channel and a material/armor footstep fixture. **Unknown:** no whole-source inventory of audio callers or original-runtime A/B comparison was performed.

### FR-LIFECYCLE-001 — Start, new session, continuing the latest save and exit

**Proposed phase: Pre-alpha.** Starting the application loads the declared content profile, initializes presentation and shows an optional startup sequence before the menu. New game enters a selected module and character; continue loads a selected/latest valid save; returning to menu or quitting leaves the previous save intact. Startup, module-loading and movie failures need an actionable state and defined recovery/shutdown sequence.

**Original observation:** main (0x401000) loads the default module and UI module data, may play intro movie 8 (the condition is not checked in the executable), then calls the main menu handler. Read without an executable check (F0), a module failure exits without a graceful shutdown or a distinct error exit status, so the original does not demonstrate robust recovery. Latest save selector sorts save entries by date; last-save window loads selected metadata then delegates to common load handler. Startup ordering and failure exits (0x401000), last-save UI path (0x544440), latest save lookup (0x403850, 0x4038C0). Steamwoven: the AREA viewer's main menu (`--main-menu`, [ARC-UI-011](../rendering/terrain-viewer.md#main-menu-arc-ui-011)) starts a new game as a pre-made hero or continues from the newest save ([MM4](../research/ledger/ui-audio.md#main-menu-arc-ui-011)); the ART viewer's ViewerSession opens/closes selected archive data only. [Viewer-only open/close lifecycle](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerSession.cs#L30-L54), [archive close](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerSession.cs#L101-L109).

**Dependencies and scenarios:** [content-product](content-product.md), [persistence model](../architecture/decisions.md#architecture-direction), UI lifecycle and error domain. Test cold start, intro disabled, missing video, failed default module, first-run with no save, continue and normal quit with state preservation. **Unknown:** this inspection did not establish all current-app OS startup/shutdown details for Steamwoven or original executable.

### FR-LIFECYCLE-002 — Save, list, overwrite, delete and preview

**Proposed phase: Pre-alpha.** Player-facing save manager lists saves with readable description, character and enough location/time context to distinguish entries. It supports create, overwrite after confirmation, load, delete after confirmation, and continue from the latest valid save; protected automatic saves cannot be deleted through the normal delete action. UI must show save/load progress and specific failure rather than claiming success.

**Original observation:** save action selects or allocates a slot, asks confirmation before overwriting, calls the game library save (0x403030) and reports success/failure. Save metadata carries module name, PC name, map, game date, portrait, level, location, story state, description and thumbnail. List UI sorts saves by date; delete confirms and calls the game library delete (0x403790); automatic save name is protected inside delete helper. Save UI action and feedback (0x5435D0), metadata fields and thumbnail creation (0x403DD0), metadata save layout (0x404010), delete confirmation and list refresh (0x543160), protected auto-save delete (0x403790). Steamwoven implements no game save manager or game persistence; ViewerSession generations prevent stale diagnostic archive/frame completions but do not persist a game state. [Viewer-only generation checks](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerSession.cs#L30-L54), [stale completion filtering](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerSession.cs#L78-L99).

**Dependencies and scenarios:** lifecycle store/API, character/world state, module id and thumbnail renderer. Test create/list/sort/overwrite/cancel/delete/protected-autosave/latest-load; remove preview or data member and ensure no success status. **Unknown:** by reading (F0), the `.gsi` reader copies variable declared lengths into fixed metadata fields without visible length caps at this call site; safety and exact malformed-save admission require broader bounds inspection. No save operation was run here.

<a id="fr-lifecycle-003"></a>

### FR-LIFECYCLE-003 — Consistent save payload, schema and load failure

**Proposed phase: Pre-alpha.** Save contains one coherent authoritative game state, including every required domain and UI state at a clear boundary. New game/save schema version, module identity and any profile compatibility are checked before mutation. Truncated, corrupt, incompatible or partially restored saves stop safely, identify the failure and preserve the previous usable session/save. Loading must not silently mix modules or leave partly replaced global state.

**Original observation:** the game library save (0x403030) writes version 25 and invokes per-module serializers with `0xBEEFCAFE` sentinel after each; it separately invokes extra UI save callback, writes metadata and archives `Save\\Current`. The game library load (0x403410) clears/restores that working directory, reads the `data.sav` version and compares it with 25, refusing another (the `data2.sav` version is read and not compared; [PS4](../architecture/original-persistence.md#1-the-slot-folder-archive-files), corrected by ARC-RES-086), invokes module loaders and checks sentinels. Main-menu caller checks save metadata version==25 before the load; after success it sets current module name from metadata. Do not infer that every module validates compatibility or that rollback is transactional. Module serialization/save payload (0x403030), load reads version and module sentinels (0x403410), caller metadata check and module identity restore (0x5432B0), UI serializer registration and module list, game library save-module registry. Steamwoven has no game save schema/store/module restore implementation; its versioned input settings JSON is a separate config preference codec. [Diagnostic settings codec only](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Input/InputSettings.cs#L23-L47).

**Dependencies and scenarios:** all domain save owners, stable schema/profile migration, module admission and backup/error policy. Test field truncation, wrong version/module, sentinel mismatch, module loader failure after earlier loads, retry into known-good save and proof old save remains intact. **Unknown:** complete per-module load callback validation, source save variants and original compatibility matrix were not audited.

<a id="fr-lifecycle-004"></a>

### FR-LIFECYCLE-004 — User settings versus save-bound state

**Proposed phase: Pre-alpha.** Audio/video/input preferences and interface options persist independently from per-campaign world state; UI indicates whether a change applies immediately or after relaunch. Resolution/window/high-DPI, key remapping, controller options and text/accessibility values need validated range, defaults, reset-to-default and graceful fallback if unavailable on a platform. Domain state such as map, inventory, story flags and game clock belongs in the save instead.

**Original observation:** settings load (0x438B50) parses key-value settings, settings save (0x438C20) rewrites changed preferences and is tied to game library lifecycle. Settings path is `arcanum.cfg` or `worlded.cfg`; a `HighRes/config.ini` reader (resolution/windowing/scroll/intro/logo keys) has no matched function in the original executable and is not the options screen. Settings configuration parsing and writeback (0x438AE0, 0x438B00, 0x438B50, 0x438C20), settings-path setup (0x4020F0), init path (0x401000). Steamwoven has project-owned input settings codec, but that covers bounded camera/actor tuning; the documented display UI lab is separate and explicitly does not persist final product/game preferences. [Input settings values/validation](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Input/InputSettings.cs#L5-L47), [UI lab boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/display-ui-validation.md#L63-L65).

**Dependencies and scenarios:** settings store, platform capability checks, user input and save module ownership. Change music volume and world setting separately, restart, load earlier game save, reset preferences and confirm only expected category changes. **Unknown:** exact original settings-file validation/atomic write guarantees are not established by these bodies.

## Explicit early non-goals and the unknown area

**Multiplayer/network/lobby/chat — an early non-goal**, not an automatic implementation target. The original contains multiplayer screens, network handlers and player export code (multiplayer functions 0x49C670–0x4A6560, 102 functions); their bodies were not audited here. The single-player menu read here (F0) does not show a multiplayer button. A few “broadcast” calls or symbols do not demonstrate working online play/chat. Multiplayer message and event handlers (0x49D690, 0x4A1F30, 0x4A1F60, 0x4A1FC0, 0x4A2020, 0x4A2040, 0x4A2070, 0x4A2A30), single-player button set. Multiplayer utility code includes a character-export confirmation, but the observed main-menu new-character flow is new/pre-generated prototype, not an identified single-player import/export flow. Multiplayer export prompt helper (0x57CFB0, 0x57D080), pre-generated character selection (0x545870, 0x5458D0, 0x5459F0, 0x545B60). Single-player import/export support remains unknown; do not assume it belongs in Pre-alpha. **Researched 2026-10-27 (ARC-RES-072, exe F2):** [the original's multiplayer](../research/multiplayer-evidence.md) — up to 8 players, the host applies the rules and broadcasts the state over its own TCP on top of WinSock (port 31435, LAN discovery over UDP 31434), WON only as a lobby; a module counts as networked if it has the file `mp.txt` (`Vormantown` has it, `Arcanum` does not); exporting a character from single player is a hidden X key in the character window, a `.mpc` file without items and companions. The addresses in this paragraph above are the earlier reading (F0); the research refines them (for example, the export prompt 0x57D080 and the overwrite prompt 0x57D150, "save character" — 0x57CFB0). Owner decision 2026-10-27 (ARC-DEV-044): the groups FR-NET-001…008 were added to the [Network play](network.md) section; network play stays outside the alpha and the early goals (the research recommends a separate direction after single player).

**Editor — an early non-goal**, separate from the game UI. The original has editor initialization/render branches and editor-only tools, including the editor draw (0x404740); their presence is not a product commitment or complete editor audit. Some text overlays explicitly disable themselves for editor view. Editor draw path (0x404740), editor config path in module loading (0x404C10), editor branch in text bubbles (0x4D5F10). Full tool inventory is outside this report.
