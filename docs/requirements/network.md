# Network play

**Current status:** the status of each requirement in this document, the implemented scope, the remainder and the documentation are in the [coverage matrix](coverage/network.md); where they differ, the matrix is correct.

The section was added on **2026-10-27** by task ARC-DEV-044 on the owner's decision ("Yes, add the FRs") from the group proposal in the [research of the original's multiplayer](../research/multiplayer-evidence.md#requirement-group-proposal) (ARC-RES-072, PR #411). The **original** below was checked against the retail `Arcanum.exe` 1.0.7.4 by two independent reads (level F2, rows [NT1–NT16](../research/ledger/multiplayer.md#multiplayer-arc-res-072) of the check ledger); function addresses and details are in the research. There were no run-time checks of the original (no games over the network). The scenarios are proposed acceptance, not executed checks. The open questions of the research (the roles of packets 81, 123, 127, subtypes 70 and 44, LAN operation on modern Windows) are in its section [Open questions](../research/multiplayer-evidence.md#open-questions).

**Stage:** not the alpha and not an early goal. The research recommends network play as a separate direction after a finished single-player game; the owner has set no date. Adding the groups to the register opens no tasks. A related step, separate from networking, is loading a second module (for example `Vormantown`) in single-player, [FR-CONTENT-003](content-product.md#fr-content-003), after the alpha (owner decision 2026-10-27).

**General product-goal boundaries (to be verified):** Steamwoven keeps the original's rules (host authority, server options, parties and experience sharing, character reset, network-play restrictions) on its own protocol. Network compatibility with the original client and the WON service is not a goal: WON is closed, and the original client needs the original's state layout. The decision on the protocol, the transport and the internet lobby stays with the owner. Cheap preparation without network code: the session owner (`Arcanum.Session`) changes state only through typed serializable operations, so that the host can later apply client requests by the same path (a conclusion of the research).

## Network play groups

<a id="fr-net-001"></a>

### FR-NET-001 — Creating and joining a network game

**Product goal (to be verified):** a player creates a game (the host plays too) or joins someone else's: LAN discovery, a bookmark list, a typed address and an internet lobby in place of WON; up to 8 players. Joining checks the password, the ban list, the protocol version and the level range. **Boundary:** no separate dedicated server was found in the original; the protocol format is not inherited. **Original** ([NT1–NT3, NT9, NT10](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): a TCP star over WinSock, the host listens on port 31435, LAN discovery is a UDP broadcast on port 31434; 8 slots, slot 0 is the host; player limit 1..8; WON is only the lobby, chat and server list, and game traffic goes from the host to the clients. A typed host name that is not an IP address is not resolved, and the join reports success (NT9, a bug of the original). **Acceptance:** a synthetic host and two clients; refusal for password, ban, version and level with a typed reason; the host name is resolved or the join reports an error. **Steamwoven:** absent.

<a id="fr-net-002"></a>

### FR-NET-002 — Host authority and state replication

**Product goal (to be verified):** the world exists once, on the host. Clients send requests (movement, a speech message, item actions, starting a spell), the host applies the rules and AI and broadcasts the result; a client does not run NPC AI and does not change shared state itself. An item picked up by one player is locked for the others. **Boundary:** the original's packet set (130 types) is not reproduced; the split of authority is reproduced. **Original** ([NT4–NT6](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): the network state word distinguishes host from client; the network test answers "apply" in single-player and, in a network game, only when a received packet is being applied; about 350 rule functions outside the multiplayer range check these flags (for example, damage is applied only on the host, a client does not run AI — CL3); object locks on pick-up, drop and moving items between containers. **Dependencies:** a single session owner and typed operations. **Acceptance:** a synthetic client does not change shared state without the host's reply; two clients do not take the same item; host and client states match after a sequence of actions. **Steamwoven:** absent.

<a id="fr-net-003"></a>

### FR-NET-003 — Network clocks and network-play restrictions

**Product goal (to be verified):** the host sets the time; a client advances within a limited budget and never rolls time back; the game waits while a client loads. In a network game combat is real-time only, there is no sleeping and no world map travel (town maps only). **Boundary:** lifting these restrictions is a separate owner decision, not parity. **Original** ([NT8, NT14, NT15](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): real-time step 5..250 ms, game time 8 × real time; the host broadcasts the time at most about once a second; the client budget is about 2 s of real time since the last synchronization, and the time is taken only if it is later than its own; a pause while a client loads; turn-based combat is rejected and both turn-based modes are switched off in the settings; resting is rejected; the world map opens the town map of the sector or closes. **Dependencies:** the game clocks ([FR-LIGHT-001](lighting-time.md#fr-light-001), [FR-LIGHT-002](lighting-time.md#fr-light-002)), combat and travel. **Acceptance:** a synthetic client with packet delay does not go past the budget and does not roll back; turn-based combat, sleeping and travel in a network game are rejected with a reason. **Steamwoven:** absent.

<a id="fr-net-004"></a>

### FR-NET-004 — Network modules, the world instance and its save

**Product goal (to be verified):** a network game can be started only on a module with the network-module marker; each game is a new instance of the module's world; a joining client receives the current map and the needed module state; the host saves and loads a network game. **Boundary:** whether to open the main campaign to network play is an owner decision: the original does not offer it (no marker), and world map travel is rejected in the network. **Original** ([NT7, NT8, NT16](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): the module list mounts every candidate and looks for a root `mp.txt` (its contents are not read); the server list takes only modules with it — in the shipped game that is `Vormantown`, `Arcanum` does not have it; the start creates an instance with a new GUID, loads the module and the save; the client receives the map files, the animation, magic-tech and trap states, the `Players` folder and the other players' characters; the multiplayer module save holds the markers, the ids of the saved PCs of departed players and the slot table. **Dependencies:** [FR-CONTENT-003](content-product.md#fr-content-003) (loading a second module in single-player, after the alpha), save/load. **Acceptance:** a synthetic module without the marker is not offered for network play; two games of one module do not share state; the host's save restores the slots and the saved PCs. **Steamwoven:** absent; the `Vormantown` module is read by the content stack (FR-CONTENT-003).

<a id="fr-net-005"></a>

### FR-NET-005 — Network game characters

**Product goal (to be verified):** a single-player character can be exported to a network character file without damaging the current game; the file holds attributes, skills, spells and technologies without items, companions and world state; import rejects a file with an inventory or companions; on joining, the character is reset and receives starting items by the auto-equip table; the server keeps a limited number of characters of departed players. **Boundary:** ready-made network characters are player data; the Steamwoven file format may be its own. **Original** ([NT13, NT16, NT10](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): export is a hidden X key in the character window, only outside a network game and not during another's turn; the game is saved to a temporary slot, the `.mpc` file is written by a destructive reset (the whole inventory, damage, combat, quests, rumors, blessings and curses, reputations, companions, flags and variables) and the temporary save is restored; auto-equip by `Rules\AutoEquip.mes` taking the background into account; the number of saved PCs is an option (10 by default). **Dependencies:** the character and skills, the character window [FR-UI-004](ui-media-lifecycle.md#fr-ui-004), the menu [FR-UI-001](ui-media-lifecycle.md#fr-ui-001). **Acceptance:** export does not change the single-player state; import of a file with items is rejected with a reason; on joining, the character is reset and equipped by the table. **Steamwoven:** absent.

<a id="fr-net-006"></a>

### FR-NET-006 — Server options

**Product goal (to be verified):** the host sets the game type (free, cooperative, role-playing — only for the server list), the number of players, the level range, a password, player killing, friendly fire, private chat, shared keys, auto-join, auto-equip and the number of saved characters; the options take effect on the host. **Boundary:** a player's personal settings (always run, auto-attack, auto weapon switch, companion skills) are separate, on the player's side. **Original** ([NT10](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): the server options word; without "player killing", PC-on-PC damage is forbidden, without "friendly fire", damage between a PC and an NPC of the same party or the same leader is forbidden; both bans are one handler (0x4A6190, the only one in its table), and it works only on the host; shared keys: off, any party member, or a party member on screen; without auto-join the host admits a player in the control window; the effect of "private chat" has not been read. **Acceptance:** synthetic PC-on-PC and PC-on-party-member damage with every combination of options; a join outside the level range is rejected. **Steamwoven:** absent.

<a id="fr-net-007"></a>

### FR-NET-007 — Player parties and experience sharing

**Product goal (to be verified):** players join into a party with the speech commands "join" and "disband"; the party shares keys and quests (what one completes closes for the others), NPC companions are not shared; experience is split equally between the living PCs of the party near the recipient. **Boundary:** this group is the network party rules; the exchange of the journaled story state on joining stays in [FR-SOCIAL-006](story-social-ai.md#fr-social-006), which this section does not replace. **Original** ([NT11, NT12](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): one party number per slot (−1 — none); joining rejects a non-player and a player already in a party and broadcasts the table; only the host awards experience, after the difficulty adjustment (+50 % or −25 %) it splits it by integer division (at least 1) between the living PCs of the same party in a screen-sized rectangle; a possible division by zero when the recipient is dead and there are no living members nearby (NT12, medium confidence, to be checked by the oracle before network work). **Acceptance:** a synthetic party of three PCs, one off screen and one dead — the split follows the rule without division by zero. **Steamwoven:** absent.

<a id="fr-net-008"></a>

### FR-NET-008 — Lobby, chat and administration

**Product goal (to be verified):** a player list, messages to all and private ones, the host admitting a player, kick and ban; notifications about a player lagging and recovering. **Boundary:** the WON chat servers and the update through Sierra are not reproduced; the internet lobby is an owner decision (FR-NET-001). **Original** ([NT2, NT6, NT10, NT16](../research/ledger/multiplayer.md#multiplayer-arc-res-072)): a request for and a broadcast of the player list, a speech message or a broadcast from a client is applied by the host, a broadcast of notifications; the multiplayer control window in place of the rest button (admit, kick, ban); the multiplayer timer drives the periodic broadcasts and departed players. **Acceptance:** a synthetic host admits, kicks and bans a client; a banned client does not join again; a private message is received only by its addressee. **Steamwoven:** absent.
