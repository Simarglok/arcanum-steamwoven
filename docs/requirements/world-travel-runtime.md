### FR-NAV-001 — A click sets the path target, while direct input sets a direction

**Behavior and acceptance.** Input must distinguish a click on a destination cell from direct direction/stick input: if a click means a path to a place, the actor searches for and follows a path to the target; if a modern build picks direct movement for a controller, that is a separate explicit input policy. Acceptance checks the same distant landmark with mouse and stick: the click route either reaches the target or reports a block; the stick does not silently turn into an attack or an object selection.

**Original and Steamwoven.** The game-interface event handler (0x54DE50) passes the selected cell to the movement or run target for that cell (click and caller (0x54DE50), movement/run targets (0x433640), run target (0x433C80)); the run conditions are checked in the exe (row [LA3, L2, L5](../research/ledger/world.md#world-movement-and-data-arc-res-047-arc-res-029-arc-res-034-arc-data-021-clock)). In Steamwoven `MovementRuntime` accepts predefined intents and step assessments, and the gamepad lab uses a direct step/near target without a detour path search ([runtime boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Simulation/Movement/MovementRuntime.cs#L4-L25), [gamepad lab limit](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/input/gamepad-movement-study.md)). **Verification boundary:** the original keyboard/mouse actions are refined in the [input requirements](original-keyboard-mouse.md) from the original's functions and the manual; full click-route execution and runtime parity are not yet confirmed.

**Current Steamwoven:** WORLD003 ties a left-stick diagnostic intent to an exact cell step/return/finish. ARC-WORLD-007 adds a Godot-free [click route core](../world/click-route-runtime.md): a direct attempt, a bounded search in a 64×64 window and a follower on top of MovementRuntime; in `area` an LMB click on a ground diamond sets the target, and the stick and quarantine (palette, focus, Reset/Reload) interrupt the route, while a started step reaches the cell center. This is a diagnostic viewer, not the product's original click route: there is no cursor/preview and no path-choice parity; running is ARC-WORLD-020 ([gait runtime](../world/gait-runtime.md)). [Viewer policy](../rendering/terrain-viewer.md#integrated-world-diagnostic-policy), [Data API](../world/cardinal-traversal-assessment.md).

### FR-NAV-002 — Passability is computed for a specific step and actor state

**Behavior and acceptance.** The movement decision accounts for the terrain/tile mask, blocking objects and their state, the step orientation, actor abilities, doors/windows, discovered traps and applicable penalties. It must not be replaced by a single visual-cell flag. Acceptance uses adjacent steps through an open and a closed door, a wall, an occupied cell, a window and a changed terrain state; the path-search result matches the attempt of the actual step.

**Original and Steamwoven.** Pathfinding (0x41F3C0) first checks the direct path, then a local detour; both branches consult tile and object traversal (windows, who can jump and the +50 cost are checked in the exe, row [W1, W2, W7](../research/ledger/world.md#world-movement-and-data-arc-res-047-arc-res-029-arc-res-034-arc-data-021-clock); the four cardinal parts of a diagonal step and closed portals — row [LV3](../research/ledger/world.md#leaving-a-building-through-a-locked-portal-arc-res-049)) (route and direct path (0x41F3C0), direct pass (0x41F840), local search and costs (0x41F9F0), tile blocker (0x4D7110), object traversal (0x43FD70, 0x43FDC0, 0x43FE00)). Steamwoven separately researches terrain obstruction and a finite set of static objects, but `MovementRuntime` receives the step assessment from the calling code and does not build a route ([step assessment boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Simulation/Movement/MovementRuntime.cs#L43-L59), [terrain components](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/research/terrain-obstruction-components-evidence.md)). **Open:** dynamic world state and general game passability are absent in Steamwoven; see [scene FR-SCENE-012/013](scene.md).

**Additional surface consequences.** The original (F0) checks a slippery cell on arrival: in the selected random/Dexterity branch it stops the current path and triggers a knockdown (arrival branch (0x4305D0)). On a location update it checks sinkable and sets/clears `OF_WADING` (location caller (0x43E770), state refresh (0x444270)). The proposed acceptance checks slipping/falling and entering/leaving the wading state separately; the exact original odds, the remaining stat/animation consequences and the actor immunity profiles need research. The conditional cost of hazards, fire and light differs from a hard blocker; fire or a dark cell cannot be declared universally impassable. The original performs these checks only under the corresponding path flags (conditional branches (0x41F9F0)). Proposed separate acceptance scenario: on one synthetic pair of routes, switch the corresponding flag off and on in turn, check that only the applicable cost component changes and that the path choice follows, with the other conditions fixed; a cell does not become a hard blocker only because of this cost. This is a proposal for a future navigation contract, not a setting accepted here for all actors and not a checked result of the original runtime.

**Current Steamwoven:** DATA008/WORLD003 implement owned cardinal and opt-in BoundedAdjacent assessment with four object legs, only x4..8/y0..3 and an isolated context. This result is consumed by the exact MovementRuntime/viewer; there is no general route search, live HP/registry/dynamic doors or crossing admission. [Viewer policy](../rendering/terrain-viewer.md#integrated-world-diagnostic-policy), [Data API](../world/cardinal-traversal-assessment.md).

### FR-NAV-003 — Physically passing through a door or window is not a map transition

**Behavior and acceptance.** Crossing a wall opening follows the portal/window rules and the actor's abilities: opening a door changes the local passage state; a window uses a separate action/restriction. The crossing itself must not move the actor to another map without a transition event. Acceptance walks in and out through an open door within one map, blocks a closed passage until a permitted action and checks a window separately.

**Original and Steamwoven.** The original sets portal/window traversal flags from critter abilities and applies them when checking the path/step (windows are checked in the exe, row [W1, W2, W7](../research/ledger/world.md#world-movement-and-data-arc-res-047-arc-res-029-arc-res-034-arc-data-021-clock); passing through a locked portal when leaving a building — rows [LV1–LV5](../research/ledger/world.md#leaving-a-building-through-a-locked-portal-arc-res-049)) (path flags (0x425BF0), portal/window in object traversal (0x43FE00), destination traversal conditions (0x43FE00)). Steamwoven does not tie terrain or scenery to actor traversal ([movement API boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Simulation/Movement/MovementRuntime.cs#L43-L59)). The door and passage contract is [FR-SCENE-014](scene.md); map transitions are described in [FR-WORLD-007, FR-WORLD-009 and FR-WORLD-014](world.md). **Open:** the exact policy for auto-opening, jumping through a window and the original exceptions is not confirmed by runtime here.

<a id="fr-nav-004"></a>

### FR-NAV-004 — A path segment limit does not become the limit of the whole target

**Behavior and acceptance.** A long movement target must be handled in the necessary number of segments or end with an explicit refusal. Acceptance picks a target more than eight cells away in free space, then behind an obstacle, and records each segment up to arrival or the reason for stopping. The number of steps returned by one call does not set the maximum distance an actor can move.

**Original and Steamwoven.** In the ordinary branch, pathfinding (0x41F3C0) truncates the returned result to eight rotations; function 0x426560 passes the buffer size, writes the maximum, the current position and the target cell, and the path consumer advances the current position (pathfinding result (0x41F3C0), caller and animation path (0x426560), path consumption (0x42E9B0)). The checked town-map route call also uses function 0x426560 (calling function (0x44EB40)). A repeated pathfinding for the same far click target after the buffer is exhausted is not established in the studied call chain. Steamwoven sets steps only on supplied assessments; there is no global click route ([movement API boundary](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Simulation/Movement/MovementRuntime.cs#L43-L59)). **Open:** re-segmentation in the original is not established within the bounds of this reading; the limit of 8 must not be read as a range.

**Current Steamwoven:** ARC-WORLD-007 [click route core](../world/click-route-runtime.md) executes at most 8 steps per segment and plans again from the cell where the actor ends up, until it reaches the target or gets an explicit refusal (`ROUTE_NOT_FOUND`, `ROUTE_EVIDENCE_INCOMPLETE`, `ROUTE_STEP_DENIED`). With ARC-WORLD-042 a target more than 32 cells away along an axis (`ROUTE_TARGET_OUT_OF_RANGE` of the local planner) is traversed along a corridor through the whole source, and a partial corridor stops at the cell nearest the target (`ROUTE_PARTIAL`). The re-plan after a segment and the corridor are project policy, not established behavior of the original.

### FR-NAV-005 — AI perception and line of fire are different checks

**Behavior and acceptance.** AI separately determines whether an actor saw or heard a target; concealment, distance, direction, obstacles and an auditory event take part in the studied checks. No direct universal lighting gate was found in the AI sight check (0x4AF260); light may act indirectly through specific stat/effect rules that cannot be generalized to all actors. An attack additionally checks range, a valid target and line of fire; successful detection does not mean a valid shot. Acceptance varies visibility and attack geometry independently.

**Original and Steamwoven.** The AI sight and hearing checks (0x4AF260, 0x4AF470) are used in selecting an observed target and in AI reactions; visibility accounts for distance/direction and the conceal/invisibility states, and hearing has separate parameters and checks (target selection (0x4AB460), sight (0x4AF260), hearing (0x4AF470)). The combat check of targets and line of fire belongs to [FR-COMBAT-004 and FR-COMBAT-007](combat-magic-tech.md). There is no game AI or combat target check in Steamwoven ([catalogue of current source modules](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src)). **Open:** only selected perception branches are studied here; the full AI state/reaction is not covered.

**Light boundary.** The direct visibility check (0x4AF260) does not read luminance; the dark-background stat branch (0x4B0490) is a separate specific effect. The full indirect chain and the original visibility policy are not confirmed.

<a id="fr-nav-006"></a>

### FR-NAV-006 — A trap is detected, avoided, disarmed or triggered

**Behavior and acceptance.** The system distinguishes a hidden from a discovered trap, a detection check, a disarm attempt and a trigger on placement/entry into its cell. A discovered trap may affect route cost; a failed disarm must keep separately observable consequences. Acceptance walks over an unknown and a known trap, avoiding it, a successful/unsuccessful disarm and stepping on it.

**Original and Steamwoven.** The original implements detection/awareness, disarm handlers and triggering; local navigation adds a penalty for a known trap, and actor movement runs a script on entry (check/detection (0x4BBE40, 0x4BBFE0, 0x4BC090), disarm (0x4BC7B0), trigger (0x4BCB00, 0x4BCB70, 0x4BCDC0), route cost (0x41F9F0), calling path of cell entry (0x4305D0)). The trap rules and their session state are implemented without a host ([trap state](../world/trap-state-runtime.md), ARC-WORLD-076); the viewer has no trap mechanism; items for placing them are noted separately in [FR-ITEM-016](items-economy.md) ([current source modules](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src)). **Open:** the full set of trap data/script outcomes is not checked.

<a id="fr-nav-007"></a>

### FR-NAV-007 — Lock picking is resolved through a skill and updates the access state

**Behavior and acceptance.** When a lockpick is used on a lockable portal/container, the game runs a skill check, accounts for the lock difficulty and the applicable tool bonus, unlocks the target on success, and on a critical failure may jam the lock and alert guards. The check must respect a broken/never-lockable/timed lock; Jammed is not to be treated automatically as a ban on a new attempt without separate confirmation. Acceptance covers success, an ordinary failure, critical failure, guards, the day/night flag and re-locking.

**Original and Steamwoven.** Item use in the UI (0x571CB0) selects the lockpick and the lock-picking skill; the animation goal reaches skill invocation; the skill use result (0x4C7160) updates the portal/container state, calls guard notification and a callback, the difficulty (0x4C8430) adds lock difficulty/tool bonus; an object timer re-locks the target, clears the jam and closes the portal; the "by day" and "by night" locks use hours 7..21 (checked in the exe, row [Lock hours](../research/ledger/world.md#world-movement-and-data-arc-res-047-arc-res-029-arc-res-034-arc-data-021-clock)) (item caller (0x571CB0), pick-lock goal, skill outcome (0x4C7160), difficulty (0x4C8430), lock getter/timers (0x441D40, 0x441DD0, 0x441E90)). There is no in-game lock picking in Steamwoven ([current source modules](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src)). Related boundaries: [FR-ITEM-004](items-economy.md) — key and item, [FR-SCENE-014](scene.md) — physical passage. **Open:** the retry behavior on a jammed lock and the original failure effects are not confirmed by runtime.

### FR-TRAVEL-001 — Town-map and world-map build different routes

**Behavior and acceptance.** A selected town-map point must give a local route target, while the world-map builds a route between sectors and checks region blocks. The user distinguishes the route from the movement itself; a map endpoint/entrance is activated only in its own transition lifecycle. Acceptance lays out a route inside a town and across the world-map with an encountered blocked sector.

**Original and Steamwoven.** The UI selects the local branch through the town-map route (0x44EB40) and the world-map branch through the world-map route (0x4207D0); the latter uses a separate sector table and checks the map terrain/blocking (route caller in the UI (0x5643E0), local town-map route (0x44EB40), world-map route (0x4207D0, 0x420900, 0x4209C0)). There is no game world/town route integration in Steamwoven ([catalogue of source modules](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src)). The actual entry/exit of a map and the transfer state belong to [FR-WORLD-007–014](world.md). **Open:** route cancellation/rebuilding in the full UI and all bounds of route search need a wider reading.

<a id="fr-travel-002"></a>

### FR-TRAVEL-002 — Travel changes the game time and reveals known areas

**Behavior and acceptance.** World-map travel advances the game clock from route distance and updates only applicable discovery/known-area state. Local map panning and revealing visual pixels do not by themselves reveal a world sector. Acceptance compares the time for different routes, visiting a sector, a known area and the return after saving.

**Original and Steamwoven.** The original's timed callback moves the party marker along the route and updates discovery; separate functions convert map distance into in-game hours and look up a known area (route callback (0x564C20), area lookup (0x4CB2A0, 0x4CB4D0), distance and time (0x564EE0)). There is no game calendar or world-map travel in Steamwoven ([catalogue of source modules](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src)). Clocks and waiting cross-reference [FR-LIGHT-001/002](lighting-time.md); map saving — [FR-WORLD-013](world.md). **Open:** the known-area lookup (0x4CB2A0, 0x4CB4D0) is not checked in the exe; the match of discovery behavior is not verified.

<a id="fr-travel-003"></a>

### FR-TRAVEL-003 — A random encounter depends on the route, area and time

**Behavior and acceptance.** Encounter eligibility, frequency, wilderness/civilized area, town suppression, time of day, sleep, terrain and encounter power/table are separate inputs; every accepted encounter interrupts route and enters the world/combat lifecycle. Acceptance uses controlled route/time/terrain combinations and an explicit seed, checking both encounter and no-encounter cases without assuming identical random outcome distribution.

**Original and Steamwoven.** The original changes the encounter frequency during sleep and accounts for the encounter level, hour, town/known area and terrain, then picks candidates by chart weights; the event scheduling is separate from the selection and stops movement on the world map before an encounter starts (encounter check (0x558DE0), terrain type (0x558FB0), weighted candidates (0x559010), event creation and interval (0x559260, 0x5594E0, 0x559550, 0x5595B0, 0x559640)). The choice of spawn positions/direction (0x5594E0) is not checked in the exe; there is no game encounter system in Steamwoven ([catalogue of source modules](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src)). Map transitions and the start of combat remain in [FR-WORLD-009/014](world.md) and the [combat section](combat-magic-tech.md).

<a id="fr-travel-004"></a>

### FR-TRAVEL-004 — Sleep and waiting have different conditions and effects

**Behavior and acceptance.** The availability of sleep depends on the region/place and the party states; waiting must not give the healing effect of sleep. Sleep supports duration variants, heals on a separate schedule and must end correctly under a preventing state. Acceptance distinguishes sleep in a permitted place, a sleep ban, waiting without healing and early waking.

**Original and Steamwoven.** The sleep window (0x57B080–0x57BAC0) separately filters the sleep and wait variants, checks the ability to wait in a town map and the party state, removes maintained spells on falling asleep and handles periodic healing/time limiting (mode/availability (0x57B180), schedule and removal of maintained effects (0x57B710), hourly effects/waking (0x57B7F0), data on the ability to wait (0x4BECC0)). There is no sleep, party healing or wait interface in Steamwoven. Time and effect expiry intersect with [FR-LIGHT-002](lighting-time.md) and [FR-MAGIC-006](combat-magic-tech.md).

<a id="fr-travel-005"></a>

### FR-TRAVEL-005 — The teleport ban is checked by the source and destination area

**Behavior and acceptance.** Any supported teleport effect checks the source actor, map, region and destination against the anti-teleport rules before changing the position; a refusal must not partially change the carried links or the position. Acceptance uses a permitted area, a forbidden source area and a forbidden destination area for the same action.

**Original and Steamwoven.** The original reads `Rules\\AntiTeleport.mes`; the ban check (0x4BDD30) accounts for the source and destination map/area. The world-map UI and magic-tech movement call this check (loading and reaction to a malformed/missing file (0x4BD9E0), area check (0x4BDD30), world-map UI caller (0x5618B0), magic-tech caller (0x4564E0)). There is no teleportation or area check in Steamwoven; see [FR-MAGIC-009](combat-magic-tech.md) and the boundaries of the transfer between maps [FR-WORLD-009/014](world.md). **Open:** variants of the rules file and the source failure messages were not checked.

<a id="fr-runtime-001"></a>

### FR-RUNTIME-001 — The game frame handles events, time and drawing consistently

**Behavior and acceptance.** The game loop accepts input/redraw/time events, performs only the game work that is due, updates the simulation before showing the result and returns to the queue without losing input. The loop of a diagnostic window or a background research job is not in itself a game runtime. Acceptance repeats one input/time sequence at different redraw rates and compares the authoritative states of actors and the world.

**Original and Steamwoven.** The original's main loop (0x401560) calls the TIG library update, the game library update, the iso redraw and the frame output, and then passes the message queue to the game-interface event handler (0x54DE50) (loop and caller (0x401560), iso redraw (0x557DF0, 0x557EA0, 0x557EC0, 0x557ED0, 0x557F30, 0x557FD0, 0x558110, 0x558130, 0x5581A0)). `ViewerApp` and `ViewerSession` in Steamwoven manage a diagnostic window, not the game simulation ([application](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerApp.cs#L82-L103), [view session](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Godot/ViewerSession.cs#L30-L54)). The scheduler order from reading the functions (three queues, one each for real, game and animation time; the due time and the order on ties; a limit of 500 events per ping; events created in a ping wait for the next one) and the proposed queue on the session clocks — [ARC-RES-046](../research/game-event-queue.md); the order on equal due times and the pass structure are checked in the exe (rows [TE3, TE4–TE7](../research/ledger/scripts.md#scripts-event-queue-and-randomness-arc-res-042-arc-res-045-arc-script-007-arc-res-046-arc-world-019)). The queue core (ARC-WORLD-022, slice E1) is implemented: [a pass runs only the due events](../world/game-event-queue-runtime.md) on three clocks with a budget; the session owns the queue and runs the pass on its own clocks (ARC-WORLD-024, slice E2), and the AREA viewer pumps it every frame in steps up to the due times, so the same game time under any split into frames gives the same state (ARC-WORLD-039, slice E3). **Open:** save restoration and the original frame rate need verification of the full runtime.

<a id="fr-runtime-002"></a>

### FR-RUNTIME-002 — Actor goals control actions and interruptions

**Behavior and acceptance.** An actor action is represented by a bounded active goal, passes through explicit states and releases/restores its resources on completion, an invalid target, interruption or removal of the actor. A failed state transition must not leave the actor permanently busy. Acceptance interrupts movement and a skill at the main phases, removes the goal during an action, then checks the return to control and a stable state.

**Original and Steamwoven.** Adding a goal (0x44D520) allocates the execution state and queues a timed event; the animation event handler (0x423560) calls the current goal/state with infinite-loop protection; the interrupt helpers remove goals according to priority (goal creation (0x44D520, 0x44D540, 0x44D730), scheduler (0x423560), interruption (0x424250, 0x424290, 0x424310), cleanup (0x44E2C0)). Steamwoven has a lifecycle of UI background tasks/sessions, but no actor goals and no game animation scheduler ([list of source modules](https://github.com/Simarglok/arcanum-steamwoven/tree/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src)). **Open:** the catalogue contains selected goal branches; the state graph of the animation functions (0x421B00–0x437D00, 327 functions) has not been viewed in full.

<a id="fr-runtime-003"></a>

### FR-RUNTIME-003 — An action frame triggers a game event once

**Behavior and acceptance.** Animation frame advance and game time are separate but consistent: an attack, skill, door action or other event fires at the given action frame boundary at most once; a cancel before the boundary does not cause a deferred duplicate. Steps and attacks use separate calling paths. Acceptance advances frames across the action boundary, repeated ticks, an interruption and a restart, checking the event count and the authoritative result.

**Original and Steamwoven.** The original's animation branches compare the frame with the action frame minus one (for the attack checked in the exe, rows [RT8, RT9, RT11](../research/ledger/combat.md#real-time-combat-arc-combat-004)); function 0x42E9B0 manages movement and calls the footstep sounds on selected Walk/Run frames; the attack has a separate handler (movement frame branch (0x42E8B0), footstep sound (0x4305D0), attack frame (0x432700, 0x432990)). The Steamwoven ART metadata keep `ActionFrame`, and `AnimationTimeline` plays the selected sequence without producing game events ([ART metadata](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Data/ArtTypes.cs#L48-L77), [timeline](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/src/Arcanum.Presentation/Animation/AnimationTimeline.cs#L1-L7)). Attack timing is cross-linked with [FR-COMBAT-006](combat-magic-tech.md). ARC-COMBAT-004 added a rule for frame-by-frame attack playback: the hit once at the action frame, shot repeat, the pace from Speed and weapon speed ([contract](../world/real-time-combat-runtime.md)). **Open:** the full event map, a host that plays the attack, and the match of the cadence with the original at run time are not established.

<a id="fr-runtime-004"></a>

### FR-RUNTIME-004 — An actor's appearance is resolved from race, gender, body and equipment

**Behavior and acceptance.** The choice of an actor's appearance accounts for the body/race/gender, the combat mode, the weapon/shield selectors, the armor type/palette, and the chosen animation and direction. Putting on or taking off a visible item updates the current ART in line with the authoritative equipment state; an unavailable combination reports a refusal or uses only an explicitly given substitution rule. Acceptance compares two supported body/gender combinations, a weapon/shield change, putting on/taking off armor and a combat mode switch, checking the ART selector and the equipment slot.

**Original and Steamwoven.** Character creation calls the object gender and race setter (0x441C70); prototype loading sets the NPC ART; equip/unequip checks the selectors and updates `OBJ_F_CURRENT_AID` through functions 0x465020/0x465AE0 (race/gender selection callers (0x5453A0, 0x545440, 0x545490, 0x545550), base selector update (0x441C70), NPC ART assignment (0x49B340), equipment selector check (0x464D20), update on putting on/taking off (0x4677B0, 0x467860, 0x467CB0)). Character selection belongs to [FR-CHAR-003/004](characters-skills.md); the item slot/state to [FR-ITEM-005/006](items-economy.md). The Steamwoven appearance profile is limited to one direct single-layer monster record; the player, a human and composite equipment are explicitly not supported ([visual evidence](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/research/actor-visual-evidence.md), [bounded contract](https://github.com/Simarglok/arcanum-steamwoven/blob/b1245e59c585c7b7b03dd0b764e2d3e31d0f89ae/docs/rendering/actor-visual-contract.md)). **Open:** full coverage of combinations/resources and the original appearance behavior are unknown; the requirement concerns selector choice, not new frames or 3D.

**Current Steamwoven:** with ARC-UI-039 the AREA hero is drawn with the body of its race and gender (`HeroBody`, ledger HB1–HB4), in underwear. WORLD uses a fixed HumanFixed Idle/Walk, event-derived facing and historical 264-selection metadata/raster checks; MonsterRegression is kept separately. A full PC/NPC appearance/equipment compositor and the original scheduler are absent. [Viewer policy](../rendering/terrain-viewer.md#integrated-world-diagnostic-policy), [Data API](../world/cardinal-traversal-assessment.md).
