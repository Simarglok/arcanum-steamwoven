# Generated interface chrome and density-aware layout (ARC-RES-122)

Status: **concept approved by the owner on 2026-11-11 (all recommended options; Linux narrowed to SteamOS, docs and code
only); demo lab [`experiments/hd-ui-density-lab`](../../experiments/hd-ui-density-lab/README.md) built and checked
([Demo](#demo)); the viewer is unchanged.**
Work item ARC-RES-122, docs-only. Requirements: [FR-UI-007](../requirements/ui-media-lifecycle.md#fr-ui-007) (adaptive
layout, high-DPI, chosen scale; status unchanged), [FR-UI-002](../requirements/ui-media-lifecycle.md#fr-ui-002) (HUD).
Owner direction (Display, [decisions](../architecture/decisions.md)): modern resolution, high-DPI and scalable UI are
baseline, independent of HD assets.

The current HD interface replaces each original interface ART frame with a redrawn 4× frame from the player's local pack
([HD interface art](hd-interface-art.md), ARC-RES-094, U3; `interface-redraw-4x`, `tools/hd_pack/hd_pack.py`;
ARC-UI-126, 129–131, 134–136). This note asks a different question: could the **chrome** of the interface (backgrounds,
frames, borders, buttons, slots, gauges, strips) be **generated by code** at the exact pixel density of the screen,
and the layout be sized by **pixel density** (the OS display scale) rather than by window size alone, with correct
Retina on macOS, display scaling on Windows and the X11/Wayland equivalents on Linux? It ends in a concept and options
for the owner; a demo from basic templates and solid-colour placeholders follows only after the owner approves.

Evidence vocabulary as in ARC-RES-033: **source fact** (read in the cited code or document), **code fact** (read in this
repository at `origin/main` 9d35814d8), **judgement**. Godot facts are from the Godot **4.7.2-stable** tag (the version
pinned by the toolchain) and the `GodotSharp.xml` API reference of the installed 4.7.2 .NET package; nothing was run.

## Summary

- **Today the interface size follows the window, not the density (code fact).** The window runs with
  `ContentScaleMode = Disabled` (1 viewport pixel = 1 window pixel, `TerrainViewerWorld.cs`), and every window computes its
  own factor from the window size: `AreaGameBarPanel.ScreenFactor` = `floor(min(w / 800, h / 600))` (at least 1), a
  fractional fit only for HD art (`FittedWindow`). The launcher's `uiScale` setting (50–300 %, `LauncherSettings.cs`) is
  stored but never read. Nothing reads the OS scale or DPI, and nothing reacts to a DPI change. So a 27" 1440p monitor and a
  14" laptop both show the interface at full screen height.
- **Godot 4.7.2 gives a usable scale only on macOS and Wayland (source fact).** `DisplayServer.screen_get_scale` returns the
  backing scale on macOS (2.0 or 1.0) and the window's fractional scale on Wayland; on Windows and X11 it returns 1.0.
  Windows has the effective DPI (`screen_get_dpi`, scale = DPI / 96), but Godot makes the process only *system* DPI aware,
  so a second monitor with a different scale is bitmap-stretched by Windows. Linux runs X11 by default, where the DPI comes
  from the monitor's physical size (EDID) and there is no scale at all. Details in [Platform facts](#platform-facts-godot-472).
- **Concept (judgement).** (1) One scale `s` (device pixels per original UI pixel) from the OS scale times a density base
  times the player's `uiScale`, clamped so that an 800 × 600 window still fits. (2) A device-pixel grid rule: every edge and
  every line width is rounded to whole device pixels, so the chrome stays sharp at any fractional `s` (1.25, 1.5, 1.75…), which
  no raster frame can do. (3) Chrome drawn by a small kit of parametric components (panel, frame, button, slot, gauge, strip,
  scroll, tab) with theme tokens and procedural materials, rendered by canvas shaders at device resolution; finer detail
  appears only where the density allows it. (4) Pictures stay art: illustrations, portraits, item and spell icons, the
  paper doll, the world map and the main menu picture keep the Legacy frame or the local HD pack. (5) The kit and its default
  theme are our own code, so unlike the HD pack they can be in git and in the player's package.
- **What it costs (judgement).** The look moves away from the original's painted panels unless the theme is tuned to it, the
  layout must be known as rectangles for every window (most are already in the ledgers, some exist only as painted pixels),
  text baked into panel art must become drawn text, and Windows mixed-DPI and Linux X11 stay imperfect without engine work.
- **Recommendation:** option B of [Q1](#q1-direction) (generated chrome with art pictures), density rule with fit clamp
  (Q3 b), our own metrics in device pixels rather than Godot's content scale, runtime shaders with an optional bake cache.

## Concept

### 1. One scale from density

`s = k × B × u`, then `s = min(s, W / 800, H / 600)` for the full-screen windows, where `k` is the OS scale of the screen the
window is on, `B` the density base in logical points per UI unit, `u` the player's `uiScale` / 100 and `W × H` the window in
device pixels. The HUD strips and the play-view panels follow the anchoring of [ARC-RES-093 C](../research/screen-size-and-ui-layout.md#c-recommendation)
at the same `s`; the world view takes what is left.

`B = 1.5` is the proposed base (judgement): one UI unit was about 0.37–0.43 mm on the 15–17" monitors the 800 × 600 game was
made for; a Windows logical point at 96 DPI is 0.265 mm, so 1.5 points is about 0.40 mm. On a 14" MacBook Pro at its default
mode (1512 × 982 points, about 0.20 mm a point) 1.5 points is 0.30 mm and 600 units take 900 of 982 points.

| Screen (OS setting) | `k` | Today, HD art (fractional fit; Legacy art takes its floor) | Concept `s` | Interface height |
| --- | ---: | ---: | ---: | --- |
| 14" MacBook Pro, default (3024 × 1964 device px) | 2 | 3.27 | 3.0 | 1800 of 1964 px |
| 27" 4K on macOS, "looks like 2560 × 1440" (5120 × 2880) | 2 | 4.8 | 3.0 | 1800 of 2880 px |
| 24" 1080p, Windows 100 % | 1 | 1.8 | 1.5 | 900 of 1080 px |
| 27" 1440p, Windows 100 % | 1 | 2.4 | 1.5 | 900 of 1440 px |
| 15.6" 4K laptop, Windows 250 % | 2.5 | 3.6 | 3.6 (clamped from 3.75) | full height |
| 1280 × 800 handheld, X11, no scale | 1 | 1.33 | 1.33 (clamped from 1.5) | full height |

The change is on large desktop monitors: the interface keeps a physical size and more world shows, instead of the interface
growing with the monitor. The player's `uiScale` stays the override in both directions. The scale is recomputed on
`dpi_changed` (macOS, Wayland), on a change of the window's screen (all platforms, polled, since Windows and X11 send no
notice), and on a resize.

### 2. Device-pixel grid rule

The chrome is laid out in UI units and converted to device pixels with fixed rounding (judgement, the usual rule of vector
interface toolkits):

- an edge at `x` units goes to `round(x × s)` device pixels; a rectangle's width is the difference of its rounded edges, so
  neighbours never gap or overlap;
- a line or border of `w` units is `max(1, round(w × s))` device pixels and lies inside its rectangle; a hairline stays one
  device pixel at every `s`; nested bands of a frame are stacked by their rounded widths (not by rounding each band's
  edge), so equal bands stay equal;
- the price is a small drift of thickness: four 1-unit bands are 8 device pixels at `s = 1.5` (6 exact) and 4 at `s = 1.25`
  (5 exact); the outer rectangle never drifts, the interior absorbs the difference;
- radii, bevels and gradients are computed in device pixels with one device pixel of anti-aliasing;
- hit tests stay in UI units (as today), so input does not depend on rounding.

A raster frame cannot follow this rule at a fractional `s`: a 1× frame drawn Nearest at 1.5 doubles every other pixel
column, and a 4× frame minified to 1.5 blurs its one-unit lines over two device pixels. Generated chrome is sharp at every
`s`. The [synthetic comparison](#synthetic-comparison) shows the difference on a frame drawn by this note's own script.

### 3. What is generated and what stays art

Kinds from the ARC-RES-094 census:

| Kind (census) | Share of pixels | Concept |
| --- | ---: | --- |
| panels ≥ 300 px, mid panels | 86 % | split: the frame, background, bevels, sockets, separators and slot grids generated; a painted illustration inside a panel (main menu picture, paper doll, map, book pages) kept as a picture |
| strips (top and bottom bars) | 1 % | generated, centred 800 units with generated side fill (solves the missing side piece, ARC-UI-096) |
| buttons (2–4 frames) | 2 % | generated plate and states (idle, hover, down, disabled) with a picture glyph where the original has one |
| gauges (vials, bars, pips) | 0.5 % | generated: the fill is a value, not a frame sequence |
| icons | 2.4 % | pictures (Legacy or HD pack) |
| cursors | 0.1 % | pictures (Legacy nearest, as decided in ARC-RES-094) |
| animations and overlays | 1.3 % | pictures; the compass and hover overlays may be generated later |
| bitmap fonts | 6.4 % | text (see [section 7](#7-text)) |

Pictures are drawn at `s` from the Legacy frame or the HD pack, as today (trilinear from 4×; for Legacy at fractional `s` a
"sharp" upscale: Nearest to the next whole multiple, then linear down, judgement).

### 4. Component kit and theme

A kit of parametric components, each a pure description in UI units plus a drawer:

- `Panel` (background material, inner shadow), `Frame` (a list of bands from outside in: width in units, colour or material,
  light/dark bevel side, optional rivets at corners or on a pitch), `Button` (plate, bands, glyph slot, four states),
  `Slot` and `SlotGrid` (inventory cells, sockets), `Gauge` (vial, bar, pips; fill from a value), `Strip` (the HUD bars with
  socket holes for buttons and gauges), `Scroll`, `Tab`, `Slider`, `TextField`, `Tooltip`, `Separator`, `PortraitFrame`;
- **theme tokens**: palette, band widths, radii, bevel strength, materials with seeds, per window class; a window is
  layout (rectangles in units, from the ledgers) + tokens;
- **materials**: wood, brass, iron, leather, parchment as deterministic procedural shaders (noise, grain direction, wear,
  edge highlights) or as small tileable swatches; swatches made by us are in git, swatches cut from the original stay local.

### 5. Detail by density

The "HD" of generated chrome is detail that only appears where it can be seen: a feature is drawn when its smallest part is
at least one device pixel. At `s = 1.5` a brass band is a flat light-dark bevel; at `s = 3` it gains engraving lines, rivet
highlights and wood grain. Material noise is defined in UI units with octaves cut at the device-pixel frequency, so the look
is the same at every `s` and only fineness grows, with no shimmer on resize (judgement).

### 6. Rendering in Godot

| Way | What | For | Against |
| --- | --- | --- | --- |
| G1 runtime | `Control` nodes sized in device pixels; one canvas-item shader per component kind (signed distance of the rounded rectangle and bands, bevel light from the distance gradient, `fwidth` anti-aliasing, material noise); `StyleBoxFlat` for the flat cases | exact at any `s`, nothing to rebuild on a scale change, no assets | a material per item breaks canvas batching (dozens of panels, judged harmless); the shader is new code to test |
| G2 bake cache | G1 drawn once per (component, size, `s`) into a texture (a `SubViewport` render or CPU), then drawn as a texture | cheapest per frame, works with nine-patch | cache invalidation on scale change and resize; memory |
| G3 vector files | our own SVG templates through the experimental `DPITexture` | authoring in a vector editor | experimental API; it follows canvas oversampling, which the viewer does not use (content scale disabled) |
| G4 density buckets | a build step renders the kit to PNG atlases at 1×, 1.5×, 2×, 3×, 4× and the viewer picks the next bucket up | familiar (Android-style) | fractional `s` is minified again (the blur of section 2); a build step and storage |

Recommended: G1, with G2 only if profiling asks. Layout in device pixels by our own metrics (as `display-ui-lab` did), not
by `Window.content_scale_factor` in `canvas_items` mode: the viewer already runs with content scaling disabled, and the
engine's scaling does not round edges and line widths to device pixels (judgement; the alternative is listed in Q3).

### 7. Text

Generated chrome is sharp only if its text is too. Three ways: (a) keep the original bitmap fonts and their traced 4× frames
(ARC-DEV-361), minified to `s` (soft below 4×, the current HD path); (b) a vector font built locally from the traced outlines
([font vectorization](../research/font-vectorization.md)) and drawn by Godot's text server at the device size (derived, so
local only); (c) a free-licence font in git for the generated windows. Text baked into panel art (engraved titles, labels)
has to become drawn text when its panel is generated; its census is open.

### 7a. Vector shapes

Round and curved parts (brass rings, lenses, round buttons, rivets, rounded plates, arcs) are vector shapes: a few numbers
(centre, radii, ring width, bevel width, light direction, colours) evaluated as a signed distance per device pixel in a
canvas shader, with a one-device-pixel anti-aliased edge. They stay sharp at any `s` and change live by changing their
parameters, with no new art. Ornaments too complex for a formula can be authored as our own SVG and rasterized at the
current `s` (Godot's experimental `DPITexture`, or a bake step of G2); that stays a later choice. The demo's brass ring
with a glass lens is such a shape (`LensRing.gdshader`: ring width, light direction and glass tint change with keys).

### 8. Provenance and distribution

The kit, the shaders, the default theme and our own swatches are code and data written for this project (MIT), so they can
be in git and in the player's package: every player gets a sharp interface without building an HD pack (ARC-DEV-003 is
deferred). Rectangles of the original windows are layout facts already recorded in the ledgers. A theme tuned to the
original by measuring its art (colours, band widths) is derived from it and would stay local like the pack; a theme tuned by
eye is ours (see Q2). Pictures keep their present rule (Legacy from the installation, HD pack local only).

### Q1 Direction

- **A. Keep redrawn packs, add only the density scale.** Smallest change; art stays local-only and soft at fractional `s`;
  every new window needs a redraw.
- **B. Generated chrome, pictures from art (recommended).** Sharp at any density, in git and in the package; costs a kit, a
  theme and the rectangles of every window; the look depends on the theme.
- **C. Everything generated**, pictures replaced by our own simple ones. Loses the original's illustrations; not recommended.

### Q2 Look of the default theme

- **a. Close to the original by eye (recommended):** the original's palette and forms (dark wood, brass rims, rivets, parchment)
  chosen by eye, in git.
- **b. Measured from the original:** closer, but derived, so a local theme next to the pack, with (a) as the shipped default.
- **c. A cleaner Steamwoven style** with the same layout.

### Q3 Scale rule

- **a. Fit to the window (today):** the interface always fills the height.
- **b. Density with a fit clamp (recommended):** `s = k × 1.5 × u`, capped by `min(W / 800, H / 600)`.
- **c. Pure density** without the clamp, full-screen windows scrolled or shrunk on small screens.
- Engine path: our own device-pixel metrics (recommended) or Godot's `content_scale_factor` in `canvas_items` mode (less code,
  no device-pixel rounding).

### Q4 Linux driver

**Decided 2026-11-11 by the owner: only SteamOS is a Linux target, through docs and code, with no VM run** (see the SteamOS
row of [Platform facts](#platform-facts-godot-472)). The options below are kept for the record.


- **a. Prefer Wayland** (`driver.linuxbsd = "wayland"`): exact fractional scale; the fallback without Wayland needs a check.
- **b. Keep the default (X11):** scale from the player's `uiScale` and an EDID estimate; blurry or tiny under Wayland sessions.
- Recommended: (a) after the demo checks it in the Linux VM.

### Q5 Windows with two monitors of different scale

- **a. Accept system DPI awareness (recommended for now):** sharp on the main monitor, stretched by Windows on another.
- **b. Per-monitor-v2 through a custom manifest and our own `WM_DPICHANGED` handling:** needs engine-side work and a
  Windows test machine; a later task if the owner plays that way.

  both (both are anti-aliased gradients), so its gain is the live parameters, not sharpness.

## Synthetic comparison

The task drew the corner of one synthetic frame (four bands of one UI unit, our own geometry and colours, no original
art; a throwaway Pillow script outside git) three ways at `s` = 1.25, 1.5 and 1.75: generated with the grid rule, a 1×
raster drawn Nearest, and a 4× raster minified with a box filter (the stand-in for trilinear minification). The image was
posted in the task thread and is not in git. Local observation: the generated bands are one colour and equal (1, 1, 1, 1
device pixels at 1.25; 2, 2, 2, 2 at 1.5 and 1.75); the Nearest raster gives unequal bands (1, 1, 2, 1 at 1.25; 1, 2, 2, 1 at
1.5; 2, 2, 1, 2 at 1.75; counted along one row across the left side); the minified raster mixes neighbouring band colours
into in-between pixels at every `s` (5, 6 and 7 distinct colours in that row against the frame's 4).
