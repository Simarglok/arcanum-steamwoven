# Проверка гипотезы: разрастание задач из-за декомпозиции и критериев приёмки

Дата: 14.10.2026. Гипотеза владельца: задачи разрастаются (десятки карточек и запусков, бесконечные
циклы коррекций и диагностик) прежде всего из-за плохой декомпозиции и плохих критериев приёмки.
Метод: копия доски, сравнение двух когорт по одинаковым метрикам и корреляции по 27 корням
с первым запуском ≥ 30.09. Признаки извлекались регулярными выражениями — это грубые оценки.

## Итог

**Гипотеза подтверждается частично и уточняется.**

- **Форма декомпозиции по стадиям не различает успех и провал.** И гладкие, и проблемные корни
  разбиты одинаково: PREFLIGHT → PLAN → IMPL → PUBLISH → MERGE. RENDER-007 был аккуратно
  декомпозирован заранее и всё равно встал.
- **Различает то, что положено в одну рабочую единицу.** У гладких корней один headless-результат,
  1–3 компонента, явные «не цели» и **письменно исключённые** GUI/device-гейты. У проблемных
  в один монолитный IMPL сложено всё сразу: результат, нативные GUI-наблюдения, физическое
  устройство, а у DATA-009 — неограниченное доказательство («exhaustive source certificate for
  every … managed allocation»). На этот IMPL приходится основная масса запусков (13–24).
- **Количество критериев и требований к доказательствам не различает** (медиана критериев
  у проблемных даже ниже: 5,5 против 7; доля «receipt/hash/ledger» одинакова). Различают:
  - упоминания GUI/физических гейтов (ρ = +0,45 с запусками, +0,58 с карточками);
  - «mandatory / required / must» (ρ = +0,40 с запусками, +0,71 с карточками);
  - длина тела корня (ρ = +0,49 с карточками; медиана 15,2 тыс. против 10,5 тыс.);
  - **правки контракта после первого запуска**: у 4 полностью гладких корней — 0 правок;
    у проблемных — 17–52 правки и десятки комментариев «amend / supersed / OWNER_».
- **Инфраструктура остаётся причиной сама по себе.** Нечитаемые карточки и отсутствие terminal
  встречаются в 4 из 5 проблемных корней. DATA-010 — чистый случай квоты и сбоя плагина при хорошей
  декомпозиции (7,7 тыс. символов, AC1–AC5, один компонент, 1 правка).

## Что из этого следует для плана (F6, F11)

Корень проблемы — не стадии, а **нарезка работы и форма критериев**. Предлагаемые правила готовности
карточки к работе (Definition of Ready), проверяемые guard-плагином при создании и планировщиком
при intake:

1. **Один результат — один PR.** Не больше 3 компонентов. Если больше — нарезать по вертикали на
   несколько Work-Item, каждый из которых даёт сливаемую ценность.
2. **Только критерии, которые агент может проверить сам.** Наблюдения человека, физическое
   устройство и нативный GUI — отдельный Work-Item «валидация владельцем», который не блокирует
   merge (см. F6).
3. **Каждое доказательство конечно.** Слова «exhaustive / every / certificate / worst-case / parity»
   допустимы только с явной границей: перечень случаев, лимит, эталон.
4. **Контракт замораживается при первом запуске.** Изменение — только явной поправкой владельца,
   и она обнуляет бюджет.
5. **Бюджет доказательства** (принят владельцем): по умолчанию ≤ 8 карточек, ≤ 20 запусков,
   ≤ 2 DIAG на Work-Item; при превышении — вопрос владельцу, а не новая диагностика.
6. **Размер.** Тело корня ≤ 10 тыс. символов (медиана гладких — 10,5 тыс.), стадийная карточка ссылается
   на корень, а не пересказывает контракт; доказательства — во вложения и файлы.

Ограничения анализа: признаки найдены регулярными выражениями по тексту тел и событий; один блок
мог попасть в несколько категорий; выборка — 27 корней. Качественный контраст надёжнее корреляций.
Воспроизводимые скрипты — в рабочей директории анализа (не в репозитории).
