## 1. The problem

A save keeps no goal run, no spell run, no projectile and no missile. A quick load or a map change therefore ends every NPC's action (NPCs restart their decisions), closes no pending door
(a door open at the save stays open until used), ends a maintained spell, loses a shot or a missile in flight and, today, the viewer refuses to save while the hero casts or a missile flies
(`TerrainViewerAreaQuickSave.cs`, the bug report). The original saves the animation module's run table with every goal stack (PS15), the spell-run table (PS11) and the animation and
magic events of the time queue (PS12); the objects in flight are objects and so are saved whole (PS20). MIG13 made every run a plain value (`GoalRun`, `GoalFrame`: entity strings, cells,
integers, no objects), so the table can be written as it is.

## 2. What exists after MIG13

- `GameSessionOwner._goals` is the one `GoalRunTable` (216 slots, each a `GoalRun` with its handle `{slot, runId}`, its owner entity, up to eight `GoalFrame`s, flags, `DueMs`, `PaceMs`);
  `NextRunId`, the stepping slot and the exhaustion flag are table state. The `goal.step` event (Animation domain, entity = owner, values `[slot, runId, scheduled animation ms]`) is the
  run's next step; its deadline is `GoalRun.DueMs` on the animation clock, an absolute time that the saved clocks (schema 70) already carry, so it needs no rebasing.
- `goal.step`, `spell.run`, the real-time kinds and the TB step are kinds with `Persistence = NotSaved`; `GameEventQueue.Restore` refuses a `NotSaved` kind. `GoalsReconciled` kills any
  run on the active map that has no pending step, so a restore must put runs and steps back together.
- Hosts keep a few stores outside the table (§3.3). Missiles and projectiles are session objects of the origins `missile:n` and `projectile:n` kept outside the saved stores, with
  their flight (line, pace, steps) and, for a shot, `PendingShot` in the host or the session; their counters restart at 1.

## 3. Design

### 3.1 The saved section

A new `goals` section in the snapshot (schema **72**, upgrade step from 71 adds an empty section: a save from before has no runs and loads as it did). It holds, in slot order:

- the table's `nextRunId`;
- every run that is not done and not owned by the hero (§3.4): slot, run id, owner, flags, path flags, due time, pace, and the frames bottom first (every `GoalFrame` field: goal, node, target,
  item, tile, range, sound, skill, spell run, path, path index, planned target tile, rest, frame flags, animation, frame index, count, path-pending, near, eye candy, fire round, rotation);
- nothing else of the table: the stepping slot is empty at a save point and the exhaustion flag is recomputed.

The codec validates shapes and ranges (slot below 216, at most eight frames, every goal defined, entity strings in the session's grammar, cells inside the map's cell range, flag bits only the defined ones
that a saved run may carry); the owner's `Restore` checks the rest. An owner that is not on the map is not checked by the session (the host's step ends the run of a gone object, as a destroyed NPC's); a run owned by `projectile:n` is written with its projectile (S7) and one owned by `missile:n` with its missile (S8); a run whose frame names a spell run (`GoalFrame.SpellRun`, goals 26, 82, 27, 83 and the missile's 28) is written when every run it names is saved or its slot is empty (S8, §3.5), a frame's target is an entity the session knows or the run is cut, the due time is not
behind the animation clock by more than the load's slack (a due time in the past simply fires at once, as the original's event queue does).

### 3.2 Steps come from the runs

The `goal.step` kind stays `NotSaved` (the risk-7 rule of the goal table: the animation events are re-created from the saved runs). `Restore` allocates the table, then schedules one
`goal.step` per restored run in slot order with the delay `DueMs - AnimationMs` clamped to at least 1 ms (`ScheduleGoalStep` takes a relative delay and writes the restored animation clock as payload value 2, so a due time in the past fires at once) so the equal-deadline order is the slot order, before the first pass of the frame step; `GoalsReconciled` then finds every run
stepped. A run that was mid-step at the save (the stepping slot is set only inside a step, which a save never interrupts) cannot occur.

### 3.3 Host state is rebuilt, not saved

| Store (viewer) | After a load |
|---|---|
| `AreaAiHost._arts` (animation and frame of an NPC) | rebuilt from `GoalFrame.Animation` / `FrameIndex`; an NPC with no animation run takes the art of its life state |
| `AreaAiMovers._movers` cell and facing | already saved as `npc.pos` (MIG7c); a slide in progress is lost: the NPC stands on the cell its step committed (the original writes the location at the step's start, 0x4305D0) and the run continues from its path index |
| `_routeIndex`, `_routes`, `_ownHomecomings` | recovered from the saved place (`RouteIndexOf`) |
| `_attackPlays` (start on the world clock) | restarted from the frame: the attack animation replays from its start |
| `_castFacing`, `_noRelease`, `_queuedCasts`, `_launched` | S8: `_castFacing` is set and read in the same step (never across a save); `_queuedCasts` is rebuilt from the casting goals 26/82 below a run's top that never started (node 1); `_noRelease` is asked again of the play at the action frame of a goal the host did not start (`_playedCasts`); `_launched` is not needed: the cast host's release and missile marks are rebuilt from the saved missiles; a cast whose spell run is not saved is cut |
| `AreaDoorHost` | has no store: door state is the session's openable frame plus the door's runs |
| `_passChoices`, `_usedItems`, `_listCache`, `_shown`, `_traces` | caches, dropped |

Every viewer start time is on the run-local world clock (`FrameClocks.WorldMs`, restarts at 0): none of it is saved, a restored host takes the new world time as the start of what it replays.

### 3.4 The hero's runs

The hero's runs (owner `pc`) are written in S9a–S9e: the walk, turn and states, the attack and throw, the cast with its queue, the talk, use, pickup and lock pick, and the pick pocket, each with what the viewer rebuilds from the run after a load (§6). ARC-DEV-290 (S9a) writes the hero's walk (goals 3 and 4 with what they pushed: the step 5, the turn 53, the pause; a walk that names a target is an approach's and waits), its turn (53) and its states (57, 62, 63, 31); see §6. S6 (the hero's runs) was cancelled by the owner on 2026-11-07 and reopened on 2026-11-08 as S7–S10, so a load no longer starts the hero with no run. A companion is an NPC and is saved like one.

### 3.5 Projectiles, missiles and spell runs

- **Spell runs** (S4, ARC-DEV-210, landed). The session's spell-run table (`GameSessionOwner._spellRuns`), the maintain bar and the last charged cost are the `spells` section (schema 73), and the Game-domain `magic.run` event kind
  (payload `[scheduled game ms, run slot, code]`) is made saved. **Only the settled runs are written**: the runs whose BEGIN has run and that need no host (Maintain and End actions, and the Begin action with the Processed flag: a timed run with a trigger count stays there until its first tick); a run whose BEGIN has not run (the casting goal has not released it, or the parentless run's BEGIN event is pending) or that waits for a host callback is cut with its bar slot and its events, and the goals that name it stay cut too. The overlays a settled run started (eye candy, hover) are cut with the other overlay runs (S5), so the restored run ticks to its END without them. The caster's `_released`, `_missiles` and `_itemChains` are therefore not saved in this slice (the cut runs are the ones they describe); the viewer's gates keep refusing a save while the hero casts or a missile flies. S8 saves the runs before their BEGIN that a saved goal, missile or event waits on and rebuilds `_released` and `_missiles` from the saved missiles (below); `_itemChains` still restart empty.
- **Missile objects and casts in progress** (S8, ARC-DEV-289, landed; S5's original design, cut from S6 and reopened). The session objects `missile:n` are saved in the `flights` section (schema 84: `lastMissile` and `missiles`) with their flight (`SessionMissile.Flight`, `SessionMissileFlight`: the caster's entity, the spell run, the spell, the target, the faced art, the steps per tick, the pace, the line's two tiles with the next sample, the pixel position and the line's steps, the steps taken, the art's frames and the legs), which the World host writes at the launch and at every move; their goal 28/78 runs go into the `goals` section with them. A spell run before its BEGIN is saved when a saved goal names it (an NPC's casting goal 26, 82, 27 or 83, before or after its release frame, or the missile's 28) or its BEGIN event is pending (a run cast with no parent); the goals and the spell runs are decided together (`SavedCasts`: a goal that names a run that is not saved, such as one waiting for a host callback, is cut, and the test is repeated until nothing more is cut). The cast host rebuilds its release and missile marks from the session's missiles when it is built, so the casting goal's end frees nothing and the arrival begins the run after a load; the AI host rebuilds its queued casts and asks the play again at a restored action frame (§3.3). The viewer's missile host adopts each restored missile (`SpellMissile.Rebuild`, `AreaMissileHost.Adopt`) at its run's first step on the shown map. The hero's casting goal is the viewer's (`SpellCastGoal`) and is not saved until S9, so the hero's run before its BEGIN is cut unless its missile already flies.
- **Projectiles** (S7, ARC-DEV-288, landed; S6's design, reopened). A `projectile:n` is the hero's shot or throw (`FlyShot`), an NPC's arrow or bullet (`AiLaunchShot`, ARC-DEV-282) or an NPC's thrown item (`AiLaunchThrown`, ARC-DEV-258). The original resolves hit or miss at the launch and keeps it in the projectile's fields 77–80 (SV6), so the save keeps the shot as it was decided: for the hero's shot the weapon, skill and reach it was shot with (the strike takes the hero's combatant as it is then, as before the save), the carried check's flags (outcome, miss cause, hit location, aim, weapon magic, fate, critical self-hit; not its rolls) and the boomerang's and thrown item's state; for an NPC's arrow the shooter's attack values at the shot (the whole `Combatant` and `CombatWeapon`, a test holds the codec's field lists to the records), the carried check and the target; for an NPC's throw the thrower and item. The projectile object carries its flight (`SessionProjectile.Flight`: the line's two tiles, the next sample, the pixel position, the steps, the shot flags, the art, the destination and the launch's rows by entity), written by the host at the launch and at every move; the line is rebuilt from its two tiles (`ProjectileRules.Resume`). The `flights` section (schema 80) holds the projectiles that carry a shot in flight and own exactly one live flight run, the shots they carry and the two counters; the goals section takes their goal 36 runs. After a load the viewer's projectile host adopts each restored projectile (the goal-step router builds the host at the run's first step), resolving the launch's rows again on the shown map; a flight whose rows are not there is given up as a flight that lost its map.
- Each slice that needs a section of its own raises the schema (S4: 73, S7: 80) and adds its upgrade step in `GameSessionSnapshotUpgrade.cs`.

### 3.6 NPCs open doors (GT49)

Independent of saving but listed under MIG14 in the audit (B10's neighbour, the goal table's row for door passage): the original pushes goal 11 for every walker that meets a closed portal
(GT49, the S7 read); the NPC planner and its step test read the T0 passage rule and never push it, so an NPC passes a closed door the rule admits without opening it, or never sees a door the
session closed. S3 gives the NPC walk the hero's door push over the same node ports (`DoorNode` is already written for the opener goals) and gives the NPC planner the live passages

## 5. Risks and open questions

1. **Schema.** Another thread may raise the schema; each slice merges `main` before the bump and adds its upgrade step (Opus review: schema/session core).
2. **A step under way.** The NPC's walk step is a slide between two cells; the cell is committed at the step's start. A save during a slide restores the NPC on the committed cell with the run at its
   path index; whether the next node re-issues the step or ends the walk is settled in S2 with a test (the original restores the same: the location is the committed one).
3. **Equal deadlines.** The events fire in sequence order; restoring in slot order changes the order of equal-due runs against the original's list order (not saved either; PS12 sorts by due time only).
4. **Rounds.** A save inside a turn-based round restarts combat from the critters around the hero with the order rebuilt (PS13); the saved runs of that round carry on over the rebuilt order. The
   interplay (the callback "all animations done" after a load) is checked in S2's smoke.
5. **The hero's runs** other than its walk, turn and states (S9a), attack and throw (S9b) cast (S9c), talk, use, pickup and lock pick (S9d) and pick pocket (S9e) are saved. S8 removed the viewer's gate for a flying missile and S9c the gate for a playing cast; both are saved now.
6. **Network.** Not touched (K11): the runs are plain values a client could receive.
