## Method

Behaviour comes from the retail executable (`Arcanum.exe` 1.0.7.4, SHA-256
`9bd80511…78d52`, re-hashed for this reading), read statically with `llvm-objdump`
per the [original executable check](../research/original-executable-check.md), by two
readers that each saw only the questions and the starting addresses from the
project's records (method step 6). Object fields are named from the executable's
own field name table (0x59BEA8, 338 entries including the closing `obj_f_max`), object, container and NPC flags from
its flag name tables (OF_ from 0x5BA10C, OCOF_, ONF_; each table is indexed by bit number). The direct branches of the
functions read stay inside `.text`; indirect calls go to jump tables, hook
pointers and the `CoCreateGuid` import, none to `.IIDKing`. A row at **F2** has two
readings that agree; **F1** has one reading; a disagreement is written in the row.
Everything is read from the executable unless marked **(inference)**. Steamwoven
facts come from the [audit plan](../research/architecture-audit-plan.md#layer-0-the-engine-spines)
and the [Steamwoven model map](steamwoven-model.md) (M1; its row ids D, S, V, C, L and G
are used as there) on `origin/main` d9c4fe44.

**R2 (sections 7–9).** Three question sets, each read independently by two readers who
saw only the questions and the starting addresses: sector membership and movement
(readers A1 and A2, rows RL1–RL12), what acts off the loaded sectors (B1 and B2,
RL13–RL20) and the map change order (C2 and C3, RL21–RL31; a first reader of this set
ended on an API error and was replaced). In these sections **F2** means that the two
readers of the set agree. Where a reader had not followed a point (the wading test of
RL6, the exclusion mask of RL9, the eviction history of RL20, the branches of the AI
event in RL16) or two readers differed, the author read the functions a third time; the
rows name the cases. A review of the draft by a fresh reader against the executable
corrected rows RL2, RL5, RL9, RL11 to RL13, RL16 to RL18, RL21 to RL23, RL26 to RL30 and
the statements that no AI event survives a map change. The call order of the map open is
also given by the executable's own log lines (RL27). Multiplayer branches are named where
they touch the sequence and not followed. A scripted check of the 9,670 direct calls and
jumps in the 457 functions named in sections 7 to 9 and in the readers' working lists
found every target inside `.text`, except one in 0x49D590, which is a jump table that the
disassembler read as code.

## Answer

- **Two names for one object.** In memory an object is addressed by a 64-bit
  *handle* (a pool slot with a serial number); across saves and maps by a 24-byte
  persistent *ID* (a GUID, a positional ID, or a prototype number). One sorted
  registry maps IDs to handles; it is cleared at every map change except for the
  prototypes.
- **Instances store only what differs from their prototype.** Every object has a
  prototype; a field the object has never written is read through the prototype at
  every read. Creation copies almost nothing (type, prototype, location, an ID),
  so a prototype change reaches every instance that has not overridden the field.
- **One field table for all kinds.** 337 field descriptors (0–336, 42 of them section
  markers) in fixed ranges: 36 common to every object, one block per object type (items share an item block, critters
  share a critter block), and transient fields that are never saved. Ownership is
  decided by the type alone.
- **One create path, one destroy path.** Every object the game makes at run time,
  from a blood pool to a summoned creature, goes through the same creation
  (from a prototype, or as a copy of an existing object for monster generators),
  which marks it dynamic and lists it in its sector when that sector is loaded.
  Destruction detaches the object's lights and render state and marks it destroyed;
  it stays in its sector list until the sector is freed (static objects) or the map is
  cleared, and memory is freed when the map is cleared.
- **Links are object fields, not side tables.** Leader, followers, inventory
  lists, item parent, combat focus, who hit me last, fleeing from, the enemy list,
  the substitute inventory and the ammunition/gold stacks are handle fields of the
  objects themselves. Apart from the destroyed object leaving its leader's follower
  list and its holder's inventory, they are not cleared when the target is destroyed; they
  become null IDs when the holder is saved, and null handles when a saved ID is not
  found at map open. A summoner is not stored on the summoned creature at all.

**R2: residency and the map change (sections 7–9).**

- **Sectors are a cache over one class of object.** Only walls, portals, scenery and
  traps that came from map data (the *static* objects) belong to a sector: they are
  read from its files when it loads and destroyed and freed when it leaves the cache.
  Every other object (critters, items, containers, projectiles and everything made at
  run time) lives in the object pool for as long as its map is open, loaded sector or
  not. A sector's object list shows the mobile objects standing in it only while the
  sector is loaded, and one global index finds them by sector at any time (RL1–RL4).
- **Membership is derived, not stored.** An object holds only its location. A
  relocation edits sector lists only for static objects and for loaded sectors; a
  mobile object moved into an absent sector is not listed, but the location
  notification reads the destination tile, which loads that sector, and the load's
  *fold* (RL8) lists the object (RL5, RL6). Held items are in no list and keep a stale
  location (RL10).
- **Eviction frees statics and merely detaches mobiles.** An evicted sector saves its
  changed static parts, logs its eviction time and frees its static objects; its mobile
  objects drop their render state and stay alive with all fields and timers. Only cache
  pressure evicts (16 slots, no timer, no distance rule), and whatever reads a tile of a
  sector loads it (RL7, RL11).
- **Off the loaded sectors only the heartbeat, the lights and the tile data stop.** The
  timers of mobile objects (poison, fatigue, resting, decay, restock, deferred scripts)
  fire wherever the object is; the timers of static objects reload their sector. The NPC
  heartbeat is the one timer gated by place: an NPC acts only within 30 tiles of a
  player; farther away its events only stop its animations and bring a follower to its
  leader, and its heartbeat ends when its sector is not loaded, until a fold restarts it
  (RL14–RL17). Day-night lighting is updated for loaded sectors only (RL19).
- **Nothing replays the time away.** Deadlines are absolute and fire late, elapsed-time
  handlers turn the gap into one step, a returning sector's fold puts its leaderless
  NPCs on their waypoint for the hour, and the objects and timers of another map wait in
  files until that map opens (RL20, RL28).
- **A map change closes the whole map and rebuilds the next from files.** The travellers
  are written whole into the destination's dynamic file first; then the old map is
  flushed and closed (every non-static object destroyed and freed, sectors evicted
  without saving) and the destination is loaded from its base file, differences,
  destroyed IDs, map patch and dynamic file, with no object listed in a sector until
  sectors load, and no AI event except the ones a travelling follower carries along.
  There is one request slot, and nothing rolls back if the destination fails to open,
  which leaves the game on no map (RL21–RL31).
- **For hypothesis H7 of the plan:** the original is not "only the shown area is alive".
  All objects and timers of the open map are alive; place gates exactly the NPC
  heartbeat, the ambient lighting, tile data and drawing; and no object of another map is
  in memory.

## 6. Links between objects

A link is a field of the holder (OM7): kind "handle" for a single target, kind
"handle array" for a list. In memory a handle value is tagged 0xFFFE; saved, it is
an ID. The three moments that touch links are the same for every link field:

## 7. Sectors: what a sector owns, who is listed, how objects move

A sector is a cache slot (RL2) that **owns** one class of object and only **lists**
another. The objects it owns, the *static* ones, are read from its files when it loads and
destroyed with the slot. Every other object belongs to the map: it is in the object pool for
as long as the map is open, and a sector lists it only while the sector is loaded. Sector
loading and the fold are already recorded
([SS1–SS8](../research/ledger/world.md#main-map-streaming-arc-data-030)); the rows add the
object classes, the list and index structures, relocation and its notification, and what an
eviction leaves alive. A sector id is `(y div 64) × 2^26 + (x div 64)` (0x4CFC50) and the
tile of an object inside its sector `(y mod 64) × 64 + (x mod 64)` (0x4D7090).

## 9. Map change: close the whole map, build the next from files

A map change keeps nothing of the old map in memory except its travellers, who are
written into the new map's files before the old map closes, and the queue's global
events. The follower case is [FM1–FM14](../research/follower-map-transfer.md#1-the-original-mechanism)
and the events are [P3–P5](../research/game-event-queue.md#4-persistence-and-map-change-s);
the rows add the order of the whole change and its closing and opening steps. The
executable's own log lines name the steps of the map open (RL27). The
[persistence document](original-persistence.md#4-map-change-close-and-open) reads the
same flush, close and open for what they write and read (PS22–PS31).
