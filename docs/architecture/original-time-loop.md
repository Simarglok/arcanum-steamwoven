## Method

Behaviour comes from the retail executable (`Arcanum.exe` 1.0.7.4, SHA-256
`9bd80511…78d52`, re-hashed for this reading), read statically with `llvm-objdump`
per the [original executable check](../research/original-executable-check.md), by six
readers in three question groups (the frame; the clocks and the event queue; the
turn-based gates and the mode table), two readers per group, each of which saw only the
questions and the starting addresses from the project's records (method step 6). A row
at **F2** has two readings that agree; **F1** has one reading; a disagreement is
written in the row. Everything is read from the executable unless marked
**(inference)**; **(partial)** marks code read only in part. Three points where one
reader differed were settled by a third reading of the disassembly and are named in
their rows (the lock-hour bound in TL17, the start-up menu in TL23, the repeated
subturn start in TL37). After the rows were consolidated, two independent reviewers
re-read the executable for the riskiest claims (one for TL14–TL34 and the answer points
on clocks, events and pause, one for TL35–TL46 and the round points); their corrections
stand in the rows, and the questions they settled are no longer open. An early
version of the shared listing helper dropped instructions that are exactly ten bytes
long (stores and compares of a 32-bit constant at an absolute address); the helper was
fixed and every reader redid its global searches on the full listing, with no finding
changed. The module, event type, parameter mask and map sub-module tables are read from
the file image. The network branches are noted where they cut across a row and not
followed. Steamwoven facts come from the [model map](steamwoven-model.md) (M1, §6–§7),
the session clock and event code, the viewer's frame code and the requirement coverage
rows on `origin/main` d9c4fe44.

## Answer

- **One loop on one thread, and it never waits.** After a first title-menu pass the
  game runs one loop (0x401560) for the whole session. An iteration is: engine ping
  (poll mouse and keyboard, one Windows message, sound service) → module ping (six of
  the 62 modules have a per-frame function: teleport, map, ambient sound, time events,
  multiplayer, wall fading) → redraw the game view → compose and present → drain the
  whole input queue → edge scroll. Logic is not decoupled from display. Nothing sleeps
  or waits for a timer; the only blocking call is the present, which runs only when
  something on screen changed, so (an inference from the flip call) the loop runs at the
  monitor rate while the screen changes and spins on a still one. Input read at the top of an iteration is acted on
  at its end and first drawn in the next.
- **Time is one API, stamped once per ping.** Only `timeGetTime` is used (1 ms
  resolution forced at start), and intervals are unsigned 32-bit differences. The
  module ping stamps once and hands the stamp to every module. Per-subsystem real-time
  gates (scroll 16 ms, floating text 50 ms, ambient sound 250 ms, …) fire at most once
  per frame and never catch up; there is no fixed step and no accumulator.
- **Three clocks, advanced by the time-event ping.** Real time runs 1×; game time
  and animation time run 8× the admitted interval. An interval under 5 ms is held back
  (not lost), an interval over 250 ms is cut to 250 (the rest is lost). Game and
  animation time stop together while the pause counter is non-zero; game time alone
  stops during a turn-based round; animation time keeps running in a round.
- **One scheduler for everything that happens over time.** 35 event kinds sit in three
  sorted lists, one per clock. The ping advances all three clocks first, then fires the
  lists real → game → animation against the clocks as they are at that moment, so a
  time jump made by a real-time handler is seen by the later lists in the same ping.
  Handlers' results are ignored, repeating events re-arm from "now" and so drift, equal
  due times fire newest first (events read back from a save or a map file come back
  reversed), and the 501st event taken in one ping ends that list for the ping (the
  later lists still run).
  Goal steps (animation) and every timer of the rules (poison, fatigue, decay, respawn,
  locks, the AI tick) use it; AI, combat, animation and script have no per-frame slot.
- **Pause is the Esc menu and nothing else.** One counter, one raiser: opening the
  main menu (not the options screen opened with O). It stops game and animation time
  but not real time, so sleep and travel steps, UI timers and the turn-based step
  event keep running behind the menu. Dialogs, inventory, sheet, world map, sleep,
  loading and losing focus do not pause; the loops that do not ping at all (message
  box, movie, slide show, fades) freeze all three clocks, and the next ping credits at
  most 250 ms.
- **Time jumps are additive and silent.** Sleep (+1 h per step), world-map travel
  (⌊tiles / 64⌋ h per step), the end of a round (+1 s), a timed teleport and one script
  action add to game and animation time together, ignore pause and rounds, and fire
  nothing themselves; the events that became due fire at the next list pass. Sleep and
  travel are chains of real-time events (200 ms and 62 ms apart), not loops.
- **Events follow their objects across maps.** At a map change of the PC, events of
  kinds without object parameters keep running; those whose objects all travel move
  with them; those with an object left behind (a null object counts as left behind)
  are parked in the old map's `TimeEvent.dat` and fire
  late on return; animation, magic-tech, combat, round, world-map and map-load fix-up
  events are dropped, and so are AI ticks unless they travel. A failed write loses the
  whole parked file.
- **A turn-based round is one flag on one clock plus gates.** The round flag stops
  only the game clock (+1 s per round). Everything else keeps running (the idle-fidget
  chain dies, TL30), and the round itself is made of gates: goal starters and steps,
  AI, spells and input each test "is it this critter's turn", some refusing and some
  accepting without doing. AI ticks only reschedule in a round; an NPC acts only as
  the current participant.
- **For Steamwoven.** The session clock mirrors the admission rule, but the session
  feeds its event queue one clock only (game; the queue core itself has the three
  domains), with a wider pause (any window), events fired at their own deadlines (up to
  64 steps a frame) instead of against the ping's final clock, and other time bases
  beside it for the goal machines and the frame (TL6). Details sit in the rows; the gap
  register is G1's.
