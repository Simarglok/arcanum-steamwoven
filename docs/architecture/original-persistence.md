## Method

Behaviour comes from the retail executable (`Arcanum.exe` 1.0.7.4, SHA-256
`9bd80511…78d52`, re-hashed for this reading; `Version.txt` says 1.0.7.4), read statically
with `llvm-objdump` per the [original executable check](../research/original-executable-check.md).
The first reader went through the whole save path. Three second readers, each given only the
questions and the starting addresses from the project's records for one part (the slot flow,
the module blobs, the map files and sectors), read it again independently (method step 6).
Three of the starting addresses were wrong and the second readers corrected them: the UI
library's save loop is 0x53E7C0 (0x53E790 is its unload loop), 0x4D1400 is the sector unload
(the game's loader is 0x4D1A30), and 0x4D2460 is the editor's whole-sector writer (the game's
writer is 0x4D2750). A row at **F2** has two readings that agree; **F1** has one reading. A last
reading of the riskiest rows (PS13, PS20 to PS24, PS26, PS29, PS30, PS34) against the
executable disagreed with the text on PS13, PS21, PS23, PS24, PS26, PS29 and PS30 and added
two details to PS20; the code was read again to settle each point, the rows carry the settled
text and the points that changed the first reading are listed under "Corrections". A scan of
the whole `.text` disassembly found no direct branch or call into `.IIDKing`; indirect calls
in the functions read go to the module and callback tables (every hook address in them is
inside `.text`) and to imports. Everything is read from the executable unless marked
**(inference)**. Steamwoven facts come from the
[state-owner map](steamwoven-model.md) (slice M1) and the
[session runtime contract](../world/game-session-runtime.md) on `origin/main` d9c4fe44.
Not read: the multiplayer parts, the editor-only paths, the picture codec, the light,
tile-script, sector-script and tile-block section formats inside a sector difference file,
and the table that gives each object field its storage kind (Q9).

Terms. A **module** is one row of the game library's table (62 rows) or of the UI library's
(32); a **blob** is what a module's save hook writes. A **static object** is a wall, portal,
scenery or trap without OF_DYNAMIC: it lives in the module's sector file and its changes go
to the sector difference file. A **dynamic object** carries OF_DYNAMIC, i.e. it was created at
run time (OM15–OM27); a **map-data object** is a non-static, non-dynamic object that comes from
the module's object cache. **Extinct** is OF_EXTINCT, an object that left for good (for
example by teleport, OM30). The **keep flag** is the argument of map open that stops it from
emptying the save folder first. The **fold** is the step after a sector loads that puts its
mobile objects back into the sector and starts their AI (PS31). A **locator** is an object
reference saved as id, location and map (PS18). The **start map types 1 and 2** are two
entries of the map list: the reset opens type 2 when there is one, a new game arrives at
type 1 (the map list loader was not read).

## Answer

- **A save is a folder.** The running game keeps its state in a working folder
  `Save\Current`. A slot is an archive of that whole folder (two uncompressed files) with a
  small info file and a picture beside it. Saving flushes the open map into the folder,
  writes two module files into it and packs it; loading empties the folder, unpacks the
  archive and reads the module files. Nothing saves automatically; a hotkey and the save
  window are the only ways (the character sheet's export key saves a temporary slot and
  loads it back).
- **Two kinds of state.** Global state is a short list of module blobs in `data.sav`
  (17 of 62 game modules) and `data2.sav` (6 of 32 UI modules): no outer lengths or ids, each
  blob delimited only by its own layout, the table order and a sentinel after each blob, one
  format version (25) checked for the first file. They hold the clocks and queued events,
  the script, quest and rumor globals, known areas, light and sound schemes and the sector
  history. What belongs to things (the hero's sheet, inventories, followers, reputation,
  per-hero quests) is not in those files but in object fields, saved with the objects in the
  map's files, and the changes to a map's own sectors are in its sector files.
- **Per-map files.** `mobile.md` holds the changed fields of map-data objects,
  `mobile.des` the ids of destroyed map-data objects (appended at every save),
  `mobile.mdy` every object the game created at run time, whole (the hero among them, and
  any follower or item carried in from another map); one `.dif` per changed sector holds the
  static objects' changes, tiles, lights and scripts. Initial objects come from a cache the game derives from the map's object
  files at module load.
- **A save is a map change that keeps sectors loaded.** Saving and changing map run the
  same flush; only the sector cache differs. Map close writes no objects or sectors and
  discards the in-memory map, so a load replaces the open map from files.
- **Cross-map state is parked in per-map files.** At a teleport that carries the hero away,
  the events and animation runs of whatever travels and of whatever stays behind are
  written to per-map files and merged back when that map is next entered in play (not at a
  load); the files lie in the save folder, so a slot holds them. A spell run is carried only
  when all its participants travel, otherwise it is ended.
- **A load is a reset and a replay in table order.** The menu resets the whole game first;
  the loader then empties the folder, unpacks the archive and reads each module, the Map
  module opening the saved map before the hero, combat, event and animation modules look
  objects up by id. A failure anywhere stops the loader without rollback, and the menu then
  resets the whole game again (which also empties the folder): a failed load leaves a fresh
  game, never a half-loaded one. A slot whose info has another version is refused before any
  reset.
- **The save keeps more than the hero and the flags.** It holds the event queue (24 of 35
  event types), every animation run with its goal stack, the spell-run table, the turn-based
  combat state (restarted at load, the round number is not kept), the sector eviction
  history and the script, quest, rumor and newspaper globals. It
  does not hold the random generator, AI timers (rebuilt when a sector loads), window or
  dialog state, roof changes or the user's settings (apart from one cached copy of the
  turn-based option, PS34).
- **What the comparison will need** (G1 classifies it): the original saves the spell runs and
  the animation runs with their goal stacks, which Steamwoven keeps run-local (hypothesis H9);
  it records a changed map object as the changed fields of the object itself, in one record
  format for every kind (H3); and it has one path for every object made at run time, one
  file by lifetime and not one store per feature (H2).

## Corrections to earlier records and to the first reading

Older records that this reading contradicts. None is edited here, because parallel audit
slices work in the same files; the gap register (G1) or a docs-only fix should correct them.

- The game library's load does compare the `data.sav` version with 25 and refuses another
  one (PS4). [FR-LIFECYCLE-003](../requirements/ui-media-lifecycle.md#fr-lifecycle-003) says
  the load does not compare it at top level, and the load row of
  [combat-domain-load-map](../research/combat-domain-load-map.md) says the version is stored
  and not checked.
- The info file is `save\<slot><description>.gsi` (PS1, PS5); the save-info row MW22 of the
  [UI and audio ledger](../research/ledger/ui-audio.md) names it `save\<slot>.gsi`.
- The module's mobile file lists non-static objects only, and portals are static unless
  dynamic (PS20, PS24); the "mobile objects" row of
  [main-map-streaming](../research/main-map-streaming.md) lists portals among them.
- OM10 gives the full object record to "sectors": it is used in the module's `.sec` files and
  in `mobile.mdy`, while the game's own sector difference files carry difference records
  (PS24).
- First reading changed by the code: the Map module's blob has no sentinel per sub-module and
  its save fails only if the map module is not initialised, not when no map is open (PS7);
  the `data2.sav` version is not compared (PS4); the map gender check only logs (PS29); the
  Multiplayer row writes only its sentinel in single player (PS3). The last check against
  the executable changed these: sounds of a sector are never saved (PS23); a spell run that
  does not fully travel is ended, as FM9 says, not parked (PS26); a difference record's id
  is adopted only for an object without one (PS21, PS24); the combat round counter is read
  and then overwritten by the restart (PS13); the Anim load leaves free slots untouched
  (PS30). The starting addresses given to the readers were wrong in three places and are
  listed under "Method".

Additions from [what the original saves of actions in flight](../research/original-save-in-flight.md)
(ARC-RES-096, 2026-11-08, F1; nothing above is contradicted): PS11, the record's first field is the
spell-run slot index and is read back, so slot positions survive a load, and bytes +0xC and
+0x14C..+0x157 are not saved; PS15, the animation save has no owner or player-character filter,
and the load ends with a recount that frees runs of an invalid goal type; PS20, the exact
`mobile.mdy` test is field 19 bit 0x2000 set and bits 0x1 and 0x800000 clear, with no type or
prototype exclusion (so projectiles and spell missiles in flight are written); PS30, the order
reset, then the modules, is confirmed at the menu load 0x5432B0.

## Open questions

- Q1. Whether any sector can be locked when a flush runs (such a sector is skipped by a
  save and freed unsaved by a map change); the lock holders were not traced.
- Q2. The clock a sector sees while the Map, MagicTech-Post and Player modules load is the
  reset clock, not the saved one (the TimeEvent module loads later). The effect is on the
  3000 ms flag of the first AI event of each NPC in those sectors (PS8, PS31); the AI
  handler's use of the flag (it sets an NPC flag and takes extra branches, 0x4AD200) was not
  read. Positional object ids resolved during map open and rebind (PS29) can also load
  sectors before the clock is restored.
- Q3. What an item becomes after a load when its holder was destroyed (R1 Q5). The dynamic
  save tests only the item's own flags, so an item left in a destroyed holder's list is
  written like any dynamic object with its parent turned into a null id (OM30); whether the
  reloaded item is placed by its own location field or left unplaced was not read.
- Q4. The formats of the light, tile-script, sector-script and tile-block sections of a
  `.dif`, and the `.sec` version gating of the sections after the roofs (PS23).
- Q5. What happens to the events, animation runs and spell runs of an NPC (or a group
  without the hero) sent to another map: the parking is gated on the teleported object being
  a player character (0x40DA20 tests the object's type) and, for an NPC alone, only its
  record moves and the destination map is not opened (FM1), so none is parked for it; what
  the global queues do with its events afterwards was not checked. The second half (whether FM6's removal of the object's AI events runs
  before or after the carry of PS26 inside 0x4D3460, FM8) is answered by
  [RL23 and RL28](original-object-model.md#9-map-change-close-the-whole-map-build-the-next-from-files):
  the carry comes first.
- Q6. The record formats of the `Anim.dat` and `MT.dat` files and of the run records behind
  them (0x4221C0, 0x44F3C0), the goal-type table (0x5B03D0) that decides which runs may
  travel, the Anim module's 18 ints, which Intgame hot-key record types hold ids and which
  hold numbers, and the per-type event callbacks (a save filter that the TimeEvent save
  consults and a remove callback used for parking and drops): their entries in the
  executable's table are zero and whether they are set at run time was not checked.
- Q7. The multiplayer parts of the save, the callers of the flush in the multiplayer code
  (0x49D590, 0x4A33F0) and the roles of the open sites that print no path (0x417D76,
  0x4D4C86, 0x525FC6).
- Q8. What the restart's eye-candy Anim events do in a loaded game (PS30): whether the
  installed `CombatEyeCandy.mes` animates anything, and so whether a leftover Anim event can
  drive a saved run twice or keep an orphan run alive. The restart's other effects (a
  rewritten critter flag word, the first NPC's turn start skipped while the in-load flag is
  set, the interface callbacks) were seen and not followed.
- Q9. The table that gives each object field its storage kind (built at init into the
  descriptor table of OM7, 28-byte entries with the kind at offset 0x18, at 0x5D1104; not
  read, so no object record can be produced from this document yet) and the layout of the
  array header (PS21). One further read that tabulates the kinds would close this; it needs no
  slice of its own.
- Q10. What the sector acquire does when a sector load fails, for example on a
  difference-record id mismatch (PS24), and what the player then sees.
