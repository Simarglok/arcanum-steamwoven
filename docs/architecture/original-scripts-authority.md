## Method

Behaviour comes from the retail executable (`Arcanum.exe` 1.0.7.4, the same file the
earlier slices read), read statically with `llvm-objdump` per the
[original executable check](../research/original-executable-check.md), by six readers in
three question groups (script attachments and script state; authority and the change
path; the interface mode machine and input), two readers per group, each of which saw
only the questions and the starting addresses from the project's records (method
step 6). A row at **F2** has two readings that agree; **F1** has one reading; a
disagreement is written in the row. Everything is read from the executable unless marked
**(inference)**; **(partial)** marks code read only in part. Two points where the readers
of one group differed were settled by a third reading of the disassembly and are named in
their rows (the tile script's store-back in SA18, the walk or run choice in SA47). The "only", "never" and "no other" claims that
carry a count were checked by listing the callers or the references of the function or
address in the whole `.text` listing; the counts are in the rows. Two independent reviewers
then re-read the executable for the riskiest claims (one for SA1–SA35, one for SA36–SA55);
their corrections stand in the rows. The shared listing helper keeps instructions of every length (the R4 helper had dropped
ten-byte instructions; this one does not). Step 5 of the check was scripted over every address the readers and this document name
(946 code addresses, 61,556 direct branches): every direct branch stays inside `.text`; the
44 hits outside it are jump tables decoded as code (0x4A1C98 in the packet dispatcher,
0x4EEB44 and 0x4EEB78, the key tables at 0x54C730..0x54C884, 0x54E9A4 in the game view,
the prototype builder's tables near 0x49A600..0x49AB60), not branches. The network branches are followed as far as
SP8 needs them (who applies, who sends, who requests); the transport is not. Steamwoven
facts come from the [model map](steamwoven-model.md) (M1, §1, §3, §5, §6) and the
scripting, session and viewer code on `origin/main` c7e81acf.

## Answer

- **A script is an object field, inherited from the prototype until first written.**
  Field 32 (`obj_f_scripts_idx`) is a sparse array of 12-byte attachments indexed by the
  attachment point: 32 local flag bits, four byte counters and the script number. An
  object that never wrote it reads its prototype's array; the first write on an
  instance copies the prototype's whole array into the object and then changes one
  element, and marks the field modified. From then on the attachments, their flags and
  their counters belong to that object: they are saved, copied and carried to another map
  with it by the generic object code, which has no special case for scripts. Nothing at
  run time was found writing a prototype's scripts after the prototype is built (whether a
  script operand can resolve to a prototype is open, Q3).
- **A run works on a copy and writes the whole record back once.** The object entry
  point takes a snapshot of the slot, runs the interpreter on a copy, and if the copy's
  number, flags or counters differ from the snapshot it writes all twelve bytes over the
  slot. "Remove" and "change this script" are deferred to that writeback; a script on
  another object is changed at once. There is no guard against nested runs and no merge:
  an inner run on the same slot survives only if the outer run changed nothing. The
  dialog action is the one place that commits the run's flags and counters in the middle
  of a run.
- **Other script state is global or on the PC.** 2000 global variables, 3200 global
  flags and one story number are module globals saved in `data.sav`; PC flags and PC
  variables are fields 272 and 273 of the PC object (any other object reads 0 and
  ignores writes). A run's ten local variables live on the stack and start at zero. Tile
  scripts and the sector script belong to the sector, not to an object; a tile script's
  changes to itself are never stored back. A deferred script call is a time event that
  runs a fresh record and writes nothing back.
- **There is no single change path.** About 360 functions test the network state word;
  about 300 of them are ordinary rule functions that carry their own three-way branch:
  single player applies, the host applies and broadcasts, a client sends a request or
  does nothing. The raw primitives (field set with 9323 call sites, create, move) know
  nothing of the network. A block of about 60 network-aware wrappers exists, but it is
  mainly the script layer's route: the action executor calls 21 of them and never the raw
  field setter 0x406D40. Single player has no command queue, journal or undo: apart from
  the deferred kinds of SA34 (the one teleport request, WallCheck's flag, time events and
  goals), every change is applied at its call site, and the single-player branch is the
  host's apply code without the send.
- **Player actions on a client become requests at the rule function, not at the
  interface.** Moving by a click, adding a goal, casting, learning a spell, changing
  combat mode, the dialog choice, item moves and uses, raising a base stat by one and
  follower orders each send their own packet from inside the rule function the interface
  calls; the host runs the same function and replicates the result.
- **The interface is one mode stack of 21 mode numbers (0–20; 12 is unused).** One function pushes or pops a mode,
  runs the old mode's leave case and the new mode's enter case, refreshes the cursor and
  always succeeds. Windows (dialog, barter, world map, sleep, logbook, inventory kinds,
  character sheet, loot, steal, schematic, book) replace the top mode; the follower order
  target, the quantity picker and the matchmaker are pushed over it, and the spell, skill
  and item-use target modes are pushed over an inventory when their target is an item
  and replace the top mode otherwise.
  Leaving a spell or skill target mode pops once more.
- **A click becomes a goal through a few fixed calls.** The main loop hands every input
  record to the game-view handler, which acts only in modes 0, 1, 2, 3, 16 and 18. In mode
  0 a pick (with a mask set by combat mode and Alt) gives a tile or an object; a tile
  becomes a walk or run request, an object a goal kind chosen by its type and combat mode
  (R5's names: talk 21, use object 38, use container 81, pick up 15, attack 18 or attempt
  attack 19, throw 37; a trap gives the walk kind 3 to its location, GS26), which is built
  and added through the goal
  system's add function. The target modes call the spell, skill or item-use start
  directly. The goal kinds and what the goal system does with them are R5's.

## What this reading says for H6 and H8

- **H8 (script state keyed by the home map record instead of carried on the object).**
  The original keeps attachments, their flags and their counters on the object itself,
  inherited from the prototype until first written and then owned. Moving, copying or
  saving an object needs no script-specific code. Steamwoven's keys under the home map's
  record are a different model; G1 classes it.
- **H6 and SP8 (no single command boundary).** The original has none either: authority
  is decided inside each rule function, and the network game meets the player's commands
  at those functions. A Steamwoven command boundary would be a design choice of its own,
  not a copy of the original; G1 weighs it. The original's single player applies a change
  at its call site, except the deferred kinds of SA34, with the same code the host runs.
