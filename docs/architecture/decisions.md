# Architecture direction

These are accepted product directions, not claims of implementation. Detailed implementation ADRs follow evidence from research.

| Decision | Direction |
|---|---|
| Independent runtime | No fork of, and no runtime dependency on, any reconstruction of the original's source; MIT for independently authored work. |
| Technology | C# core/data; Godot 4 presentation. Current pins and existing assemblies are recorded in [toolchain](../workflow/toolchain.md) and [status](../project/status.md); future boundaries still require evidence. |
| Original data | Read the player's original formats. Preserve identifiers and distinguish raw data from domain mapping. |
| Simulation boundary | Authoritative world/game state independent of rendering, UI and physical input. |
| Visual modes | Shared simulation for Legacy and later Remastered visuals; intended switching preserves world/action state. |
| Early graphics | Legacy first. Later upscale existing assets one-to-one; no new directions/frames or 3D required. |
| HD pack (2026-10-16) | Upscale of existing frames, characters and objects first. First set at 2×; after the measured plain upscales were rejected the same day (the edge kept its steps), the owner chose "1 + 3": a 4× soft-edge pack as the base (2× stays supported) and a generative experiment (ARC-RES-038); the pack format stays method-agnostic. A pack is built on a device from a recipe or imported from another of the owner's devices (e.g. Mac to a 16 GB Steam Deck class handheld), with per-device HD budgets. The owner builds the pack locally from his own installation; it stays outside the repository and is not distributed (pack, frames, screenshots and recordings never enter git). Git holds only code, the manifest format and the build recipe. Contract: [HD presentation](../rendering/hd-presentation-contract.md). |
| HD pack, generative re-detailing (2026-10-18) | Closed for now: the local generator checks (ARC-RES-038, ARC-RES-053) are finished; Z-Image-Turbo, FLUX.2 klein-4B and Qwen-Image-Edit-2511 (with and without the Lightning LoRA) are rejected, and the pack stays a 4× pack without generated images (the non-generative 4× base of the "1 + 3" decision). HD support in the code stays; building the pack is a separate, later task. Evidence: [HD alternatives](../rendering/hd-interface-art.md) (ARC-RES-053). |
| Display | Modern resolution, high-DPI and scalable UI are baseline, independent of HD assets. Viewport must not define simulation rules. |
| Controls | Keyboard/mouse retain original Arcanum actions and UI semantics; WASD actor movement is not a product binding. Custom controls and interface belong to gamepad mode. The [original-input requirements](../requirements/original-keyboard-mouse.md) define evidence and diagnostic-key boundaries. Keyboard/mouse and first-class gamepad. Xbox Series Bluetooth target: left stick moves actor; right stick moves camera. Historical ARC-GPAD-002/003 lab defaults invert both camera axes; current integrated WORLD defaults are false/false, independently configurable and separately persisted. Manual camera cancels follow; after camera and actor stop, actor-only movement resumes recentering. WORLD is diagnostic integration, not original-runtime parity or physical Bluetooth validation. ARC-GPAD-004 adds WORLD-only LT-out/RT-in camera zoom; actor, assets and UI are not scaled by it. See [vision](../project/vision.md). |
| Platform sequence | Develop/research on macOS now; validate Windows/Linux/handheld support later. |
| Compatibility | Original game is the principal behavioral reference; mods/patches need explicit versioned profiles. |
| Original verification (2026-10-17) | The retail 1.0.7.4 executable is the only reference for original behaviour. Single functions of the unchanged file may be executed in an emulator as an oracle that compares them with Steamwoven ([method](../research/original-executable-check.md#function-emulation-oracle)); the install stays unchanged and generated inputs and outputs stay local. Final goal: the source reconstruction is excluded from the process and the repository documents, replaced by executable readings, oracle tests and the game's data ([research and plan](../research/original-oracle-research.md), ARC-RES-051); the interim rule that kept the reconstruction as a domain's first reading until migration is superseded by the 2026-10-18 removal row below. Only free tools with free licences are used; paid or licence-restricted tools (IDA) are not. |
| Reconstruction removed (2026-10-18) | Owner decision: the source reconstruction the early studies read is removed from code, tools, tests and documents entirely, research and history sections included (option "full removal"). Facts cite executable addresses and ledger rows. Where a fact came from before the removal is kept only in git history (ARC-DEV-009 onwards, [plan](../research/original-oracle-research.md#plan)). The chosen option also named re-reading every fact in the executable; the twelve implemented functions still at F0 were read and raised to F2 (ARC-DEV-025, ledger IF1–IF12), and the remaining facts stayed at F0 without an owner decision on when to re-read them (settled 2026-10-20, next row). |
| Re-reading F0 facts (2026-10-20) | Owner decision (ARC-DEV-030): facts not yet read in the executable keep their address at evidence level F0 and are re-read domain by domain, when the domain is implemented. A task that implements or changes an original function whose facts are F0 reads that function in the executable first ([original executable check](../research/original-executable-check.md)); there is no separate campaign to re-read every F0 fact. |

| Item spells answering their own damage, MG46 (2026-10-28) | Owner decision ("делаем узкий фикс", ARC-MAGIC-025, ledger [IC9 and MG46](../research/ledger/spell-runs.md#life-item-triggers-outside-the-attack-arc-magic-024)). The bug: a spell an item event starts runs with the item's holder as its parent, so its damage step takes the holder as the attacker and walks the worn items of both sides again, and the item executor has no recursion guard. An item therefore fires again on the damage of its own spell or of a spell it caused: weapon 6130's `Target_Hit` spell fires again on its own damage until the target dies or the weapon's cells run out, and two wearers of armour 8215 (`Parent_Hit`) answer each other until one dies. The Original setting keeps it (`MagicAnomalyProfile.ItemRunDamageFiresHooks`). Steamwoven keeps every event and every first answer and only cuts the repeat: each item fires at most once in one chain of item spells (a walk of the damage step of a run an item event started skips the items that started that run or a run before it). This replaces ARC-MAGIC-024's broader fix, which fired no parent hit and no damages opponent at all for an item spell's damage. Not settled, to revisit if needed: a chain is followed only within the session (runs are not saved, so a maintained item spell loaded from a save starts a new chain), and a single item answering two different chains still fires in each. |
